# Agent Skills и MCP: две парадигмы расширения возможностей агентов

## Введение: что нужно после MCP?

В десятой главе мы подробно разобрали, как MCP (Model Context Protocol) через стандартизированный протокол решает задачу подключения агента (Agent) к внешним инструментам. Вы уже научились давать агенту доступ через MCP к базам данных, файловой системе, API-сервисам и другим ресурсам. Вспомним типичный сценарий использования MCP:

```python
from hello_agents import ReActAgent, HelloAgentsLLM
from hello_agents.tools import MCPTool

llm = HelloAgentsLLM()
agent = ReActAgent(name="Ассистент анализа данных", llm=llm)

# Подключение к MCP-серверу базы данных
db_mcp = MCPTool(server_command=["python", "database_mcp_server.py"])
agent.add_tool(db_mcp)

# Теперь агент может обращаться к базе данных
response = agent.run("Найди 10 сотрудников с самой высокой зарплатой")
```

Этот код работает хорошо: агент успешно подключается к базе. Но когда задача становится сложнее, проявляются тонкие проблемы:

```python
# Более сложный запрос
response = agent.run("""
Кто в компании обладает наибольшим влиянием?
Нужно учесть:
1. Уровень управления и число подчинённых
2. Уровень зарплаты и динамику повышений
3. Стаж и стабильность
4. Межотдельческое влияние
""")
```

Такая задача требует нескольких запросов к базе: результат каждого влияет на стратегию следующего. Ещё важнее — агенту нужны **предметные знания**: как измерять «вес» человека в организации, по каким измерениям анализировать данные и как объединять результаты нескольких запросов в вывод.



Здесь возникают две фундаментальные проблемы:

**Первая — взрыв контекста.** Чтобы агент гибко работал с базой, MCP-сервер обычно отдаёт десятки или даже сотни инструментов (разные таблицы, разные методы запросов). Полные JSON Schema этих инструментов при установлении соединения попадают в системный промпт и могут занять десятки тысяч токенов. По отзывам разработчиков из сообщества, один только Playwright MCP-сервер занимает около 8% окна контекста в 200k токенов; в многоходовом диалоге это быстро накапливается, раздувает стоимость и снижает качество рассуждений.

**Вторая — разрыв возможностей.** MCP решает задачу «можно подключиться», но не задачу «знать, как пользоваться». Доступ к базе не значит, что агент умеет писать эффективный и безопасный SQL; доступ к файловой системе не значит, что он понимает структуру конкретного проекта и его нормы разработки. Это как выдать новичку права на все системы без инструкции и лучших практик.

Именно это и закрывают **Agent Skills**. В начале 2025 года Anthropic после появления MCP предложила концепцию Agent Skills, которая привлекла широкое внимание индустрии. Один разработчик сформулировал так: «Skills и MCP — разные вещи: Skills — это предметные знания, которые говорят модели, *как* действовать, по сути продвинутый Prompt; MCP же стыкуется с внешними инструментами и данными.» Другие считают: «От Function Call к Tool Call, затем к MCP и Skills — суть примерно одна: эволюция инженерных практик и форм представления.»

Итак, что такое Agent Skills? Чем они принципиально отличаются от MCP? Это конкуренция или дополнение? В этой главе разберём эти вопросы.



## Что такое Agent Skills?

### Ключевая идея дизайна

**Agent Skills — это стандартизированный формат упаковки процедурных знаний.** Если MCP даёт агенту «руки» для работы с инструментами, то Skills дают «инструкцию по эксплуатации» или SOP (Standard Operating Procedure, стандартную операционную процедуру) — как правильно этими инструментами пользоваться.

Идея опирается на простой, но глубокий вывод: **связность (Connectivity) и способность (Capability) должны быть разделены.** MCP фокусируется на первом, Skills — на втором. Такое разделение ролей даёт ясную архитектурную выгоду:

- **Роль MCP**: стандартизированные интерфейсы доступа — чтобы агент мог «дотянуться» до данных и инструментов внешнего мира
- **Роль Skills**: предметная экспертиза — чтобы в конкретной ситуации агент знал, *как комбинировать* эти инструменты

Аналогия: MCP похож на USB-интерфейс или драйвер — он описывает, как устройство подключается; Skills похожи на прикладное ПО — они описывают, как с помощью подключённых устройств решать конкретные задачи. Можно иметь отличный драйвер принтера (MCP), но без знания, как в Word задать поля и двустороннюю печать (Skill), эффективно печатать всё равно не получится.

### Постепенное раскрытие: выход из ловушки контекста

Главная инновация Agent Skills — механизм **постепенного раскрытия (Progressive Disclosure)**. Информация о навыке делится на три уровня; агент подгружает их по мере необходимости: детали не теряются, когда они нужны, и контекстное окно не забивается всем сразу.

#### Уровень 1: метаданные (Metadata)

В дизайне Skills каждый навык лежит в отдельной папке; ядро — Markdown-файл `SKILL.md`. Файл обязан начинаться с Frontmatter в формате YAML, где заданы базовые сведения о навыке.

При старте агент сканирует все установленные папки навыков и **читает только Frontmatter каждого `SKILL.md`**, загружая эти метаданные в системный промпт. По замерам метаданные одного навыка занимают около **100 токенов**. Даже при 50 навыках начальный расход контекста — около 5 000 токенов.

Это резко контрастирует с типичным MCP: при подключении клиента к серверу обычно запрос `tools/list` сразу тянет полные JSON Schema всех инструментов и может мгновенно съесть десятки тысяч токенов.

#### Уровень 2: тело навыка (Instructions)

Когда агент по запросу пользователя решает, что навык высоко релевантен текущей задаче, включается второй уровень: читается полный `SKILL.md` — подробные инструкции, предостережения, примеры — и всё это попадает в контекст.

Агент получает всё нужное для задачи: структуру БД, шаблоны запросов, замечания. Расход токенов зависит от сложности инструкций и обычно лежит в диапазоне 1 000–5 000 токенов.

#### Уровень 3: дополнительные ресурсы (Scripts & References)

Для более сложных навыков `SKILL.md` может ссылаться на другие файлы в той же папке: скрипты, конфиги, справочники. Агент **загружает эти ресурсы только когда они нужны**.

Например, структура навыка обработки PDF может выглядеть так:

```
skills/pdf-processing/
├── SKILL.md              # Основной файл навыка
├── parse_pdf.py          # Скрипт разбора PDF
├── forms.md              # Руководство по заполнению форм (только для задач с формами)
└── templates/            # Шаблоны PDF
    ├── invoice.pdf
    └── report.pdf
```

В `SKILL.md` дополнительные ресурсы можно ссылать так:

- Когда нужно разобрать PDF, агент запускает скрипт `parse_pdf.py`
- Когда задача — заполнение форм, подгружается `forms.md` с подробными шагами
- Шаблоны открываются только при генерации документов нужного формата

У такого дизайна два ключевых преимущества:

1. **Практически безграничный объём знаний**: через скрипты и внешние файлы навык может «нести» знания далеко за пределы окна контекста. Например, навык анализа данных может включать файл на 1 ГБ и скрипт запросов: агент обращается к данным через выполнение скрипта, не загружая весь набор в контекст.

2. **Детерминированное исполнение**: сложные вычисления, преобразования данных, разбор форматов отдаются коду — меньше неопределённости и галлюцинаций LLM.

### Эффект постепенного раскрытия: с 16k до 500 токенов

Практические кейсы сообщества хорошо показывают силу Progressive Disclosure. В реальном сценарии:

- **Классический путь через MCP**: прямое подключение к MCP-серверу с большим числом определений инструментов — начальная загрузка **16 000 токенов**
- **После обёртки в Skill**: простой Skill как «шлюз», в Frontmatter только описание функций — начальный расход всего **500 токенов**

Когда агент решает, что навык нужен, он подгружает подробные инструкции и по необходимости вызывает нижележащие MCP-инструменты. Архитектура сильно снижает стартовые затраты и делает управление контекстом в диалоге точнее и эффективнее.

### Разница с инженерной точки зрения

Разберём на конкретном примере: агент, который помогает команде делать code review.

**Роль MCP**:

```python
# MCP даёт стандартизированный доступ к GitHub
github_mcp = MCPTool(server_command=["npx", "-y", "@modelcontextprotocol/server-github"])

# Инструменты, которые отдаёт MCP (упрощённый пример):
# - list_pull_requests(repo, state)
# - get_pull_request_details(pr_number)
# - list_pr_comments(pr_number)
# - create_pr_comment(pr_number, body)
# - get_file_content(repo, path, ref)
# - list_pr_files(pr_number)
```

MCP даёт агенту возможность «уметь» ходить в GitHub и вызывать эти API. Но он не знает, *что следует* делать.

**Роль Skills**:

```markdown
---
name: code-review-workflow
description: Выполняет стандартный процесс code review: стиль кода, безопасность, покрытие тестами и др.
---

# Рабочий процесс code review

## Чек-лист проверки

При code review действуйте по шагам:

1. **Получить сведения о PR**: вызвать `get_pull_request_details`, чтобы понять контекст изменений
2. **Разобрать изменённые файлы**: вызвать `list_pr_files` и получить список файлов
3. **Проверка по файлам**:
   - Для `.py`: соответствие PEP 8, явные проблемы производительности
   - Для `.js/.ts`: необработанные Promise, устаревшие API
   - Для тестов: покрыты ли новые пути кода
4. **Проверка безопасности**:
   - Нет ли захардкоженных секретов (ключи, пароли)
   - Нет ли рисков SQL-инъекций или XSS
5. **Обратная связь**:
   - Критичные проблемы: сразу комментировать через `create_pr_comment`
   - Предложения по улучшению: вынести в итог

- Новые функции — с unit-тестами (покрытие > 80%)

Поняв различия, видим: **Skills и MCP не конкурируют, а дополняют друг друга**. Лучшая практика — сочетать их в слоистой архитектуре:

**Типичный рабочий процесс**:

1. Пользователь спрашивает: «Кто в компании обладает наибольшим влиянием?»
2. **Слой Skills** распознаёт задачу анализа данных и загружает навык `mysql-employees-analysis`
3. **Слой Skills** по инструкциям навыка дробит задачу: управленческие связи, сравнение зарплат, стаж и т.д.
4. **Слой MCP** выполняет конкретные SQL-запросы и возвращает результаты
5. **Слой Skills** по предметным знаниям навыка интерпретирует данные и собирает сводный анализ
6. Пользователю возвращается структурированный ответ

Преимущества такой архитектуры:

- **Разделение ответственности**: MCP отвечает за «возможности», Skills — за «мудрость»
- **Оптимизация стоимости**: постепенная загрузка сильно снижает расход токенов
- **Поддерживаемость**: бизнес-логика (Skills) отделена от инфраструктуры (MCP)
- **Переиспользование**: один и тот же MCP-сервер могут использовать несколько Skills

## Техническая реализация: как создавать и использовать Skills

### Подробно о спецификации SKILL.md

Разберём стандартную структуру файла `SKILL.md`:

```markdown
---
# === Обязательные поля ===
name: skill-name
  # Уникальный идентификатор навыка, именование kebab-case

description: >
  Краткое, но точное описание:
  1. Что делает навык
  2. Когда его следует использовать
  3. В чём его основная ценность
  # Важно: description — единственная опора агента при выборе навыка, пишите ясно!

# === Необязательные поля ===
version: 1.0.0
  # Семантическая версия

allowed_tools: [tool1, tool2]
  # Список инструментов, которые навык может вызывать (белый список)

required_context: [context_item1]
  # Контекстная информация, нужная навыку

license: MIT
  # Лицензия

author: Your Name <email@example.com>
  # Автор

tags: [database, analysis, sql]
  # Теги для классификации и поиска
---

# Заголовок навыка

## Обзор
(подробное введение: сценарии использования, технический фон и т.д.)

## Предварительные условия
(окружение, зависимости и т.п.)

## Рабочий процесс
(пошаговое описание, как агенту выполнять задачу)

## Лучшие практики
(опыт, предостережения, типичные ловушки)

## Примеры
(конкретные кейсы, помогающие агенту понять применение)

## Устранение неисправностей
(частые проблемы и решения)
```

### Принципы качественных Skills

По официальной документации Anthropic и лучшим практикам сообщества эффективные Skills строятся так:

#### 1. Точный Description

`description` критичен для решений агента. Он должен:

- **Чётко задавать область применения**: избегать расплывчатого вроде «помогает с данными»
- **Содержать триггерные ключевые слова**: чтобы агент мог сопоставить намерение пользователя
- **Показывать уникальную ценность**: отличать навык от других

❌ **Плохой description**:
```yaml
description: Обработка запросов к базе данных
```

✅ **Хороший description**:
```yaml
description: >
  Переводит бизнес-вопросы на естественном языке в SQL и анализирует
  демо-базу MySQL employees. Подходит для запросов по сотрудникам,
  статистики зарплат, анализа отделов, истории смены должностей.
  Используйте, когда пользователь спрашивает о сотрудниках, зарплатах или отделах.
```

#### 2. Модульность и единая ответственность

Один Skill должен закрывать одну чёткую область или тип задач. Если Skill пытается сделать слишком много:

- Description становится слишком широким, точность матчинга падает
- Инструкции раздуваются и зря тратят контекст
- Навык сложно поддерживать и обновлять

**Рекомендация**: вместо одного «универсального анализа данных» — несколько узких навыков:
- `mysql-employees-analysis`: анализ базы employees
- `sales-data-analysis`: анализ продаж
- `user-behavior-analysis`: анализ поведения пользователей

#### 3. Приоритет детерминизма

Для сложных задач, где нужна точность, лучше скрипт, а не генерация LLM. Например, при экспорте данных вместо того, чтобы просить LLM собрать бинарный Excel (легко ошибиться), напишите отдельный скрипт; в SKILL.md достаточно указать, *когда* агент должен его вызвать.

#### 4. Стратегия постепенного раскрытия

Разумно используйте три уровня, раскладывая информацию по важности и частоте использования:

- **Тело SKILL.md**: основные рабочие процессы и частые шаблоны
- **Доп. документы** (например, `advanced.md`): продвинутые сценарии и крайние случаи
- **Файлы данных**: крупные справочники; доступ через скрипты по необходимости

### Практический кейс: Skill анализа сотрудников MySQL

На реальном примере из сообщества Anthropic разберём применение Agent Skills. Навык анализирует официальную демо-базу MySQL `employees`.

#### Структура файлов навыка

```
skills/mysql-employees-analysis/
├── SKILL.md          # Основной файл навыка (метаданные и подробные инструкции)
└── db_schema.sql     # Справка по схеме БД (опционально, по необходимости)
```

#### Пример ядра SKILL.md

Frontmatter навыка (слой метаданных):

```markdown
---
name: mysql-employees-analysis
description: >
  Переводит бизнес-вопросы на естественном языке в SQL и анализирует
  демо-базу MySQL employees.
  Подходит для запросов по сотрудникам (например, «данные сотрудника с номером 12345»),
  статистики зарплат (например, «отдел с самой высокой средней зарплатой»),
  анализа отделов (например, «распределение численности по отделам»),
  истории смены должностей (например, «карьерный путь сотрудника») и т.п.
version: 1.0.0
allowed_tools: [execute_sql]
tags: [database, mysql, sql, employees, analysis]
---

# Навык анализа базы сотрудников MySQL

## Обзор

Навык предназначен для анализа официальной демо-базы MySQL `employees`.
В ней около 300 000 записей виртуальных сотрудников за 1985–2000 годы.

**Ключевые возможности**:
- Понимать бизнес-вопросы на естественном языке

## Типичные шаблоны запросов

### Шаблон 1: базовые сведения


-- Запрос базовых данных конкретного сотрудника
SELECT emp_no, CONCAT(first_name, ' ', last_name) AS full_name,
       gender, birth_date, hire_date
FROM employees
WHERE emp_no = <номер_сотрудника>;


### Шаблон 2: текущее состояние


-- Сотрудники с самой высокой текущей зарплатой (TOP 10)
SELECT e.emp_no,
       CONCAT(e.first_name, ' ', e.last_name) AS name,
       s.salary
FROM employees e
JOIN salaries s ON e.emp_no = s.emp_no
WHERE s.to_date = '9999-01-01'  -- текущая зарплата
ORDER BY s.salary DESC
LIMIT 10;


### Шаблон 3: исторические тренды


-- История изменения зарплаты сотрудника
SELECT emp_no, salary, from_date, to_date,
       salary - LAG(salary) OVER (ORDER BY from_date) AS increase
FROM salaries
WHERE emp_no = <номер_сотрудника>
ORDER BY from_date;


### Шаблон 4: межтабличные связи


-- Средняя текущая зарплата по отделам
SELECT d.dept_name,
       COUNT(DISTINCT de.emp_no) AS emp_count,
       ROUND(AVG(s.salary), 2) AS avg_salary
FROM departments d
JOIN dept_emp de ON d.dept_no = de.dept_no
JOIN salaries s ON de.emp_no = s.emp_no
WHERE de.to_date = '9999-01-01'  -- сейчас в штате
  AND s.to_date = '9999-01-01'   -- текущая зарплата
GROUP BY d.dept_name
ORDER BY avg_salary DESC;


### Шаблон 5: сложный бизнес-анализ


-- Анализ «влияния»: иерархия управления, зарплата, стаж
WITH manager_hierarchy AS (
    -- Число подчинённых у каждого менеджера
    SELECT dm.emp_no, COUNT(de.emp_no) AS subordinate_count
    FROM dept_manager dm
    JOIN dept_emp de ON dm.dept_no = de.dept_no
    WHERE dm.to_date = '9999-01-01'
      AND de.to_date = '9999-01-01'
      AND de.emp_no != dm.emp_no
    GROUP BY dm.emp_no
),
current_salary AS (
    -- Текущая зарплата
    SELECT emp_no, salary
    FROM salaries
    WHERE to_date = '9999-01-01'
),
tenure AS (
    -- Стаж (годы)
    SELECT emp_no,
           TIMESTAMPDIFF(YEAR, hire_date, CURDATE()) AS years_employed
    FROM employees
)
SELECT e.emp_no,
       CONCAT(e.first_name, ' ', e.last_name) AS name,
       COALESCE(mh.subordinate_count, 0) AS team_size,
       cs.salary,
       t.years_employed,
       -- Простая оценка влияния (веса можно подстроить под бизнес)
       (COALESCE(mh.subordinate_count, 0) * 10 +
        cs.salary / 1000 +
        t.years_employed * 5) AS influence_score
FROM employees e
JOIN current_salary cs ON e.emp_no = cs.emp_no
JOIN tenure t ON e.emp_no = t.emp_no
LEFT JOIN manager_hierarchy mh ON e.emp_no = mh.emp_no
WHERE cs.salary > 60000  -- отсечь низкие зарплаты
ORDER BY influence_score DESC
LIMIT 20;


## Предостережения

### ⚠️ Корректная работа с полями времени

- **Текущее состояние**: обязательно фильтр `to_date = '9999-01-01'`
- **Исторические запросы**: учитывать диапазоны `from_date` и `to_date`
- **Расчёты по времени**: функции `TIMESTAMPDIFF`, `DATEDIFF` и т.п.

### ⚠️ Оптимизация производительности

- **JOIN больших таблиц**: опираться на индексируемые поля (emp_no, dept_no)
- **Агрегации**: разумно использовать GROUP BY и HAVING
- **Ограничение результата**: для демонстрационных выборок — LIMIT
- **Оптимизация подзапросов**: сложные запросы оформлять через WITH (CTE) — читаемее и часто быстрее

### ⚠️ Качество данных

- **NULL**: обрабатывать через COALESCE или IFNULL
- **Дубликаты**: сотрудник мог неоднократно менять отдел — учитывать дедупликацию
- **Охват данных**: в базе только 1985–2000 годы — следить за временными границами запросов

## Устранение неисправностей

**Проблема 1: пустой результат**
- Проверить корректность фильтра `to_date = '9999-01-01'`
- Убедиться, что номер сотрудника или отдела существует
- Проверить разумность диапазона дат

**Проблема 2: медленный запрос**
- Проверить, есть ли в WHERE условия по индексируемым полям
- Рассмотреть разбиение сложного запроса на шаги
- Разобрать план через EXPLAIN

**Проблема 3: неточная статистика**
- Различать «историю» и «текущее» состояние
- Проверить, не пропущены ли условия JOIN
- Проверить корректность агрегатных функций

## Отраслевая динамика и эволюция экосистемы

### Стандартизация и поддержка вендоров

Agent Skills предложила Anthropic, но идея уже влияет на всю отрасль.

**Anthropic Claude**:
- Claude Desktop и Claude Code нативно поддерживают Skills
- Есть официальный SDK и инструменты разработки
- Поддерживается официальная библиотека навыков

**Ответ OpenAI**:
OpenAI пока официально не приняла термин «Skills», но в обновлении марта 2025 ChatGPT получил близкие по смыслу возможности:

- **Расширенные Custom Instructions**: более сложные многошаговые инструкции
- **Memory и Context Profiles**: сохранение и переиспользование предметных знаний
- **«База знаний» в GPTs**: можно прикреплять документы и скрипты с загрузкой по необходимости

По сути это разные формы реализации идеи Skills.

**Google Vertex AI**:
В моделях Gemini Google ввела **"Grounding with Functions"**: разработчик определяет «пакеты функций» (Function Packages), в каждом:

- Определения функций (аналог tools в MCP)
- Руководства по использованию (аналог instructions в Skills)
- Примеры (examples)

Дизайн очень близок к гибриду Skills + MCP.



### Неизбежность слоистой архитектуры

Сводя мнения вместе: **Skills и MCP — два неизбежно разделяемых слоя архитектуры агентов**. С ростом сложности систем такое разделение неизбежно:

```
Прикладной слой (Application Layer)
  ↓ Agent Skills
  ↓ предметные знания, рабочие процессы, лучшие практики

Транспортный слой (Transport Layer)
  ↓ MCP
  ↓ стандартизированные интерфейсы, вызовы инструментов, доступ к ресурсам

Инфраструктурный слой (Infrastructure Layer)
  ↓ базы данных, API, файловая система, внешние сервисы
```

Это тот же путь, что и у классической программной архитектуры (от монолита к слоям и микросервисам), только заново разыгранный в AI.



### Тренды стандартизации

По мере роста внимания к агентам ожидаются такие тенденции:

### Вызовы и риски

Нужно помнить и о рисках:

**Безопасность**:
- Skills содержат исполняемые скрипты — риск code injection
- MCP-серверы могут открывать чувствительные интерфейсы данных
- Доверие к сторонним навыкам трудно проверить

**Загрязнение контекста**:
- С ростом числа Skills даже метаданные могут сильно занимать контекст
- Нужны более умные индексация и поиск навыков

**Риск фрагментации**:
- MCP идёт к стандарту, формат Skills ещё не унифицирован
- Вендоры могут выпускать несовместимые спецификации Skills



## Итоги

Agent Skills и MCP — два ключевых слоя абстракции в стеке агентных технологий:

- **MCP (Model Context Protocol)**: решает задачу «связности» — стандартизированный интерфейс агента с внешним миром, своего рода «нервная система» или «руки»
- **Agent Skills**: решают задачу «способностей» — упаковка предметных знаний и рабочих процессов, своего рода «кора головного мозга» или «инструкция»

**Ключевые выводы**:

1. **Слоистая архитектура неизбежна**: с ростом сложности систем разделение «слоя соединения» и «слоя знаний» неизбежно

2. **Эффективность контекста — центральное противоречие**: Progressive Disclosure в Skills снижает расход токенов более чем на 90% — это главное техническое преимущество

3. **Демократизация предметных знаний**: Skills позволяют вносить вклад в возможности агента и не-разработчикам — это сильно расширит границы AI-применений

4. **Гибрид — лучшая практика**: в корпоративных системах MCP даёт инфраструктурное подключение, Skills — бизнес-логику; вместе они дают эффективных и поддерживаемых агентов

**Практические рекомендации**:

- Для **подключения внешних сервисов** (БД, API, облако) предпочтителен MCP
- Для **сложных рабочих процессов** (многошаговые задачи, предметная экспертиза) предпочтительны Skills
- В **сценариях с ограниченным контекстом** (длинные диалоги, много инструментов) используйте Skills для постепенного управления
- При построении **корпоративных агентов** применяйте слоистую архитектуру MCP + Skills
