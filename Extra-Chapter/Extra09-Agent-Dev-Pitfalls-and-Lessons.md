# Глава 1. Слишком много «лучших практик» — и первая большая яма

Едва взялся за код, начитался отраслевых практик по дизайну агентов: например, урок по инженерии контекста от команды Manus и официальный материал Anthropic «Building agents with the Claude Agent SDK». Смотрю, как топ-компании щедро делятся «лучшими практиками», и думаю: раз есть Claude Code, пусть AI сразу реализует все эти продвинутые идеи?

Без раздумий навалил «элегантных» слоёв: многоуровневую память (Memory System), сложную инженерию контекста, мультиагентную систему (Multi-Agent)… Claude Code действительно силён — быстро нагенерил кучу хитрой логики.

## Провал на старте

Когда с надеждой запустил первую тестовую версию, реальность врезала по лицу: система была никуда не годной.

На совсем простой правке агент как с цепи срывался: семь–восемь инструментов, несколько раундов «левое полушарие спорит с правым». В итоге — обрезанный код, который даже не запускается, и счёт за токены с серьёзным перерасходом.

Глядя на экран ошибок, понял: разработка агента — это не классическая разработка ПО.

В обычном бэкенде мы привыкли сначала нарисовать архитектуру, потом писать код. Красивая схема — устойчивая система. Инстинкт программиста.

С агентом иначе. Вы работаете с большой языковой моделью (LLM): она вероятностна — на одном и том же входе ответы могут сильно расходиться.

Я на этом шатком фундаменте навесил сложную архитектуру, которую сам ещё не проверил. Multi-Agent, Plan-and-Execute… схемы переплетались, неопределённость росла кратно.

Итог: сложная архитектура дно не держала; из‑за слишком многих переходов состояния и перекрёстных вызовов инструментов модель ошибалась ещё сильнее. Ошибки ходили по компонентам туда‑сюда — даже разбирать было не за что зацепиться.

«Лучшие практики» крупных команд — хорошая вещь. Но я упустил: эти сложные схемы — результат бесчисленных ям и тонн сожжённых токенов, а не стартовая точка для новичка.

## Снести и начать заново

Смотря на код, который на простом чтении файла уходил в бесконечный цикл, сделал «непочтительное» решение — снёс всё и начал с нуля.

По принципу «Less is more» взял самый базовый каркас Hello-Agent и сначала прогнал самый короткий путь. Ядро сжал до нескольких блоков:

| Компонент | Главная роль |
|------|----------|
| ReActAgent | Базовый когнитивный цикл Thought → Action → Observation |
| ToolRegistry | Регистрация инструментов и маршрутизация вызовов |
| ContextBuilder | Склейка системных правил, истории и «доказательств» из среды |
| TerminalTool | Выполнение реальных команд в целевом репозитории |
| Message | Единая структура сообщений сессии |

Без модных паттернов: в `code_agent.py` просто собрал их вместе:

```python
self.terminal_tool = TerminalTool(
    workspace=str(self.paths.repo_root),
    timeout=60,
    confirm_dangerous=True,
    default_shell_mode=True,  
)
self.registry = ToolRegistry()
self.registry.register_tool(self.terminal_tool)
```

Когда убогий V0 впервые успешно прогнал минимальную задачу в терминале, выдохнул.

![Успешный прогон минимального V0 в терминале](images/Extra09-figures/1.png)

Если уже есть базовый диалог и вызов инструментов — можно проверять и итерировать на реальных задачах.

Сначала запустить важнее, чем сделать «сразу идеально».

# Глава 2. Авария с пайплайном команд: когда «недиагностируемость» убивает

После того как V0 заработал, ослабил ограничения на инструменты. Архитектура уже простая — пусть модель сама комбинирует команды?

Включил Terminal Tool с `default_shell_mode=True`: модель могла не только одну команду, но и пайпы, редиректы, подкоманды — почти как человек.

## Как это случилось

Простая просьба: «Найди определение функции `process_data`».

Модель быстро выдала «профессиональную» команду:

```bash
rg -n "def process_data" src/ | grep -v test | sed -n '1,50p'
```

Классика опытного инженера: найти определение, отфильтровать тесты, взять первые 50 строк. Вроде ок.

Результат — пусто. Агент завис на миг и начал «спасать»:

**Первая попытка:**
```
Thought: Похоже, не нашли — возможно, слишком узкий охват. Расширю поиск.
Action: rg -n "process_data" | head -100
```

Снова пусто.

**Вторая попытка:**
```
Thought: Может, имя функции неточно — попробую нечёткий паттерн.
Action: rg -n "process.*data" src/ --type py | grep "def "
```

Снова пусто.

**Третья попытка:**
```
Thought: Возможно, функции нет, или я не в той директории. Сначала посмотрю структуру.
Action: find src/ -name "*.py" | xargs grep -l "process_data"
```

Опять пусто. После трёх попыток сдался: «В репозитории определения `process_data` не нашёл; возможно, имя ошибочно или это не Python».

Я вручную заглянул в репозиторий — функция лежала в `src/utils/helpers.py`, строка 42.

## Разбор

Скопировал ту же команду в терминал — `rg` упал:

```bash
$ rg -n "def process_data" src/ | grep -v test | sed -n '1,50p'
Error: path 'src/' does not exist
```

При старте агента рабочий каталог был не корень проекта, а подкаталог. Относительно него `src/` не существует — `rg` сразу вышел с ошибкой.

Но на стороне агента ошибку съел пайп. Из‑за `|` stderr `rg` не попал в stdout как понятный сигнал агенту: дальше по цепочке шёл пустой вход; `grep` и `sed` тоже выдали пустоту.

**Ошибка в цепочке сплющилась.** Агент видел только пустую строку и не знал, что апстрим уже упал.

Хуже всего: модель на этом ложном сигнале сделала неверный вывод. Решила, что «действительно не нашла», и пошла чинить: менять запрос, каталоги, даже сомневаться в имени функции. Всё — на ошибочном допущении; токены улетали зря.

![Пустой результат пайпа скрыл ошибку rg](images/Extra09-figures/2.png)

## Неверное направление «починки»

Первая реакция: Bash слишком опасен — нужны жёсткие ограничения.

Написал кучу проверок безопасности:

```python
SHELL_META_TOKENS = ["|", "||", "&&", ";", ">", ">>", "<", "$(", "`"]
DANGEROUS_BASE_COMMANDS = {"rm", "chmod", "mv", "dd"}

def validate_command(cmd):
    # Проверка на пайпы и редиректы
    for token in SHELL_META_TOKENS:
        if token in cmd:
            return False, f"Недопустимый символ: {token}"
    
    # Базовая команда должна быть в белом списке
    base_cmd = cmd.split()[0]
    if base_cmd not in ALLOWED_COMMANDS:
        return False, f"Команда {base_cmd} не в белом списке"
    
    # Опасные команды
    if base_cmd in DANGEROUS_BASE_COMMANDS:
        return False, "Опасная команда, выполнение запрещён"
    
    return True, "OK"
```

Быстро выяснилось: shell слишком гибок. Запретили `|` — остаётся `$(...)`; запретили `>` — есть `tee`; запретили `rm` — можно обнулить файл через `> file`.

Патчей всё больше, код всё длиннее, а корень — «на каком шаге сломалось» — никуда не делся.

Даже если запереть все пайпы и редиректы и оставить только одну простую команду:

```bash
rg "pattern" src/
```

При пустом ответе всё равно неясно: «в репозитории правда нет» или «`rg` не выполнился из‑за пути». Модель по-прежнему не может целенаправленно исправлять ошибку.

## Корень проблемы

Позже дошло: корень не в «опасности команд», а в **недиагностируемости**.

Конкретно три проблемы:

**Первое: несколько шагов свалены в один Action.** Пайп упаковывает логику; промежуточные состояния теряются. Агент видит только финальный результат, не процесс.

**Второе: сигнал наблюдения — один конечный статус.** Успех, сбой и пустой результат смешаны. Модель не отличает «действительно не нашли» от «поиск упал по дороге».

**Третье: нет адресного исправления.** Непонятно, кто виноват — `rg`, `grep` или `sed`; дальше только угадывание. Повтор — не «исправить ошибку», а «испытать удачу».

Дать модели больше свободы — не поднять потолок способностей, а усилить неопределённость. Она пишет «умные» команды, но при сбое даже вы не поймёте, на каком шаге «умность» вышла боком.

## Как делаю сейчас

Bash не удалил — понизил роль: только краевые случаи, которые не закрывают атомарные инструменты; в основной цепочке его нет.

Частые операции вынес в атомарные инструменты:

| Инструмент | Назначение | Формат ответа |
|------|------|----------|
| LS | Список каталога | `{status, data: {entries}, text}` |
| Glob | Поиск файлов по имени | `{status, data: {paths}, text}` |
| Grep | Поиск по содержимому | `{status, data: {matches}, text}` |
| Read | Чтение с номерами строк | `{status, data: {content}, text}` |

У каждого — явный статус:
- `success`: задача выполнена, результат в `data`
- `partial`: выполнено, но содержимое обрезано
- `error`: сбой, в `error` — конкретный код

Например, Glob ничего не нашёл:
```json
{
  "status": "success",
  "data": {"paths": []},
  "text": "No files matching '*.xyz' found"
}
```

Путь не существует:
```json
{
  "status": "error",
  "error": {"code": "NOT_FOUND", "message": "Path 'src/' does not exist"}
}
```

Модель чётко отличает «действительно нет» от «ошибка».

Жёсткие правила для Bash тоже явные:
- Запрет читать/искать/листить: `ls`/`cat`/`head`/`grep`/`find`/`rg` — для этого есть отдельные инструменты
- Запрет интерактива: vim, nano, top, ssh
- Запрет сети (по умолчанию): curl/wget
- Чёрный список: `rm -rf /`, sudo/su, mkfs/fdisk

После этого отладка стала проще. Смотришь лог — видишь шаг:
- Glob вернул пустой массив → файла правда нет
- Glob вернул `NOT_FOUND` → путь неверный
- Grep вернул timeout → слишком широкий охват

По коду ошибки модель выбирает следующий шаг: путь плохой — сменить путь; таймаут — сузить; правда нет — сказать пользователю.

## Вывод главы

**Диагностируемость — предпосылка восстанавливаемости.**

Не знаешь, что сломалось — не починишь. Не знаешь, на каком шаге сбой — не исправишь точечно.

В разработке агентов «свободная композиция команд» звучит красиво, а на деле делает чёрный ящик. Эффективный пайп сплющивает ошибки в неразличимую пустоту — и модель всё дальше уезжает по неверному пути.

Атомарные инструменты шагов больше, зато у каждого ясный вход, выход и статус. Сломалось — локализуешь; модель ошиблась — поправишь.

**Управляемость важнее, чем «сделать задачу за один вызов».**

# Глава 3. Зона Goldilocks в дизайне инструментов — не «чем свободнее, тем лучше» и не «чем мельче, тем лучше»

После главы 2 начал дробить инструменты. Универсальный Terminal Tool действительно болел; атомарные инструменты сделали отладку яснее.

Но быстро попал в новую яму: **раздробил слишком мелко**.

## Два края, оба пройдены

### Край A: универсальный инструмент

Первый край вы уже видели. Один Terminal Tool умеет всё: пайпы, редиректы, подкоманды, переменные окружения — полный простор.

Казалось: LLM умная, дай свободу — будет как инженер. Комбинации вроде `rg | grep | sed` очень эффективны.

Чем кончилось — знаете: ошибку съел пайп, модель гадала и ретраила, токены текли, задача не решалась.

### Край B: чрезмерная атомизация

Поняв проблему универсального инструмента, качнулся в другую сторону: каждый крошечный сценарий — отдельный инструмент, «максимальная атомизация».

Список выглядел примерно так:
- `ListDir`: содержимое каталога
- `ListDirRecursive`: рекурсивный список
- `FindByName`: поиск по имени файла
- `FindByPattern`: поиск по маске
- `SearchExact`: точный поиск
- `SearchRegex`: поиск по регулярке
- `SearchFuzzy`: нечёткий поиск
- `ReadLines`: диапазон строк
- `ReadOffset`: смещение в байтах
- `ReadFull`: весь файл
- …

Проблемы пришли быстро.

**Первое: модель «не могла выбрать инструмент».**

Всё про поиск файлов — `FindByName`, `FindByPattern`, `Glob`… какой? Часто залипала уже на первом шаге и тратила несколько раундов, чтобы понять: «ага, нужен Glob».

Однажды попросил «найди все тестовые файлы»: сначала `ListDirRecursive` на всё подряд, потом хотела `SearchRegex` отфильтровать — а тот ищет по содержимому, не по имени; снова `ListDirRecursive` за контекстом; и только потом правильный `Glob`.

То, что делается за один шаг, растянулось на четыре.

**Второе: шум Schema затопил контекст.**

У каждого инструмента — описание параметров, типы, ограничения. Десяток схем — уже тысячи токенов.

Модель ещё не начала задачу, а уже тратит внимание на «чтение инструкции». Длинные schema ещё и провоцируют «избирательную слепоту»: замечает лишь часть инструментов или путает параметры.

**Третье: стоимость поддержки взрывается.**

Каждый инструмент — свои тесты, тюнинг, краевые случаи. У `FindByName` и `FindByPattern` ~80% логики общая, но это два инструмента — две кодовые базы.

Тогда и дошло: **система инструментов — не «чем мельче кубики Lego, тем лучше»**. И чрезмерная универсальность, и чрезмерная нарезка толкают систему к нестабильности: одна ломается на выполнении, другая — на выборе решения.

## Поворот: найти «в самый раз»

Позже завёл рамку: **частота × определённость**.

- **Частые, сильно определённые действия**: атомизировать; один шаг, дальше не дробить
- **Средние, со побочными эффектами**: под контролем; критичные операции — со страховкой
- **Редкие, слабо определённые**: оставить гибкость, но на нижнем «аварийном» слое: явно запрещать, а не перечислять всё разрешённое

По этой рамке пересобрал систему в три слоя:

| Слой | Примеры инструментов | Цель дизайна | Типичные ограничения |
|------|---------|---------|---------|
| Частый атомарный | LS / Glob / Grep / Read | Один шаг — одно доказательство, удобно чинить | Жёсткий контракт входа/выхода |
| Средний контролируемый | Write / Edit / MultiEdit | Изменения проверяемы и откатываемы | Read-then-write + оптимистичная блокировка |
| Редкий аварийный | Bash | Нестандартные нужды | Явные запретные зоны, не в основной цепочке |

![Трёхслойная система инструментов](images/Extra09-figures/3.png)

Слои — не «архитектурная эстетика», а ответ на реальные сбои. Главная ценность — снизить нагрузку на решение модели: частые пути короче и яснее.

## Частый атомарный слой: обязан быть стабильным

Это «основное оружие» агента; частота максимальна — стабильность критична.

### Glob: искать файлы — одного инструмента достаточно

Сначала хотел нарезать «поиск по имени» на несколько:
- `FindByName`: точное имя
- `FindByPattern`: маска
- `FindByRegex`: регулярка
- `FindRecursive`: рекурсия

Потом увидел: это как раз чрезмерная атомизация. Модель спорит сама с собой: «точное или маска? рекурсия или нет?»

Свёл в один `Glob`: одна задача — паттерн на входе, кандидаты путей на выходе.

```python
# Параметры Glob
{
  "pattern": "**/*.py",  # маска; ** — рекурсия
  "path": "src/"         # старт; по умолчанию текущий каталог
}
```

Внутри реализация может быть сложной (поддержка `**`, регистр, сортировка), наружу — простой интерфейс. Модели не нужно знать «рекурсия или нет»; достаточно сказать «найди все py-файлы».

### Grep: сложность — во внутренностях

Grep — другой пример. Внутри много оптимизаций:
- предпочитать `rg` (ripgrep) — быстро
- если `rg` недоступен (кодировка, права) — откат на Python-реализацию
- сортировка по времени изменения файла — свежие выше

Для модели же видно только:

```python
# Параметры Grep
{
  "pattern": "def process_data",  # паттерн поиска
  "path": "src/",                  # путь
  "file_pattern": "*.py"          # опционально: только нужный тип файлов
}
```

Формат ответа фиксирован:
```json
{
  "status": "success",
  "data": {
    "matches": [
      {"file": "src/utils.py", "line": 42, "text": "def process_data(...)"},
      {"file": "src/helpers.py", "line": 88, "text": "def process_data(...)"}
    ]
  }
}
```

Модель видит стабильный вход. Внутри можно усложнять (автооткат и т.д.), снаружи — простота.

## Средний контролируемый слой: менять можно, но только «после чтения»

Здесь правка файлов — «опасная операция»; нужны жёсткие ограничения.

### Жёсткий порядок Read → Edit/Write

Правило: **без Read — нельзя менять**.

```python
# Первый Read
result = Read({"path": "core/llm.py"})
# В ответе есть file_mtime_ms и file_size_bytes

# Последующие Edit автоматически получают параметры оптимистичной блокировки
Edit({
  "path": "core/llm.py",
  "old_string": "...",
  "new_string": "...",
  "file_mtime_ms": 1733920000123,  # автоподстановка
  "file_size_bytes": 4217          # автоподстановка
})
```

`ToolRegistry` держит кэш чтения. Если файл не читали, Edit/Write сразу возвращает ошибку: `"File not read. You must read before editing."`

Это мешает модели править «по памяти»: сначала содержимое должно попасть в контекст и быть подтверждено.

### Оптимистичная блокировка: защита от гонок

Даже после Read файл мог изменить внешняя программа (например, автосохранение IDE).

Edit/Write сравнивает `file_mtime_ms` и `file_size_bytes`; при расхождении — `CONFLICT`:

```json
{
  "status": "error",
  "error": {
    "code": "CONFLICT",
    "message": "File changed since last read."
  }
}
```

Тогда модель обязана снова Read, взять свежее содержимое и только потом править.

### MultiEdit: атомарные правки в нескольких местах

Иногда в одном файле нужно несколько правок. Несколько отдельных Edit посередине могут упасть и оставить файл «наполовину изменённым».

`MultiEdit` принимает пачку правок разом: либо все успешны, либо все откатываются:

```python
MultiEdit({
  "path": "core/llm.py",
  "edits": [
    {"old_string": "...", "new_string": "..."},
    {"old_string": "...", "new_string": "..."}
  ]
})
```

Так обеспечивается атомарность правок файла.

## Редкий аварийный слой: Bash можно, но не как вход по умолчанию

Bash не удалил: атомарные инструменты не покрывают все редкие сценарии. Например:
- тесты: `pytest tests/`
- зависимости: `pip install -r requirements.txt`
- git: `git status`

Но роль — «аварийный слой», не «дефолт».

### Явные запретные зоны

Список ограничений длинный, суть одна: **не делать то, что умеют частые инструменты**.

```python
BASH_DISABLED_PATTERNS = [
    # Запрет читать/искать/листить (есть отдельные инструменты)
    r'\bls\b', r'\bcat\b', r'\bhead\b', r'\btail\b',
    r'\bgrep\b', r'\bfind\b', r'\brg\b',
    # Запрет интерактива
    r'\bvim?\b', r'\bnano\b', r'\btop\b', r'\bssh\b',
    # Запрет сети (по умолчанию)
    r'\bcurl\b', r'\bwget\b',
    # Чёрный список опасных команд
    r'\brm\s+-rf\b', r'\bsudo\b', r'\bsu\b',
    r'\bmkfs\b', r'\bfdisk\b'
]
```

Если модель пытается через Bash сделать `ls`, получит: `"Use LS tool instead of Bash for listing directories."`

Так её гонят по основной цепочке атомарных инструментов, без «срезания углов».

### Зачем оставлять Bash?

Спросят: при стольких запретах не проще ли удалить Bash?

Потому что **идеальная атомизация нереалистична**. Всегда остаются края:
- свой Python-скрипт
- проверка переменных окружения
- специфичная команда сборки проекта

Частота низкая — отдельный инструмент не окупается, а потребность есть. Bash закрывает этот «длинный хвост».

Ключ: **наличие Bash не должно ломать стабильность основной цепочки**. Это «последнее средство», не «вход по умолчанию».

## Сквозные механизмы

### Единый протокол ответа

Все инструменты — частые, средние, редкие — отдают JSON одного формата:

![Единый JSON-протокол ответа инструментов](images/Extra09-figures/4.png)

Пример ответа Glob:

```json
{
  "status": "partial",
  "data": {
    "paths": ["core/llm.py", "agents/codeAgent.py"],
    "truncated": true
  },
  "text": "Found 2 files matching '**/*.py' (Scanned 12000 items, timed out)",
  "stats": {"time_ms": 2010, "matched": 2},
  "context": {"cwd": ".", "params_input": {"pattern": "**/*.py"}}
}
```

Плюсы:
- модели не учить разные форматы разных инструментов
- единая обработка ошибок: смотри `status`, при `error` — `error.code`
- удобная отладка: одна структура вывода, единые Trace

### ToolRegistry

`ToolRegistry` — не только реестр. Он ещё делает несколько важных вещей:

**1. Сводка Schema**

Параметры каждого инструмента превращает в JSON Schema и отдаёт модели единым списком:

```python
registry.get_openai_tools()  # список schema всех инструментов
```

**2. Автоподстановка оптимистичной блокировки**

Для Write/Edit/MultiEdit автоматически подставляет `file_mtime_ms` и `file_size_bytes`:

```python
def _inject_optimistic_lock_params(self, tool_name, parameters):
    if tool_name in {"Write", "Edit", "MultiEdit"}:
        path = parameters.get("path")
        if path in self.read_cache:
            parameters["file_mtime_ms"] = self.read_cache[path]["mtime"]
            parameters["file_size_bytes"] = self.read_cache[path]["size"]
```

**3. Circuit breaker (предохранитель)**

При серии сбоев инструмент временно отключается — чтобы модель не крутилась на «битом» инструменте:

```python
# 3 сбоя — отключение; через 300 с — снова доступен
if circuit_breaker.should_block(tool_name):
    return {
        "status": "error",
        "error": {"code": "CIRCUIT_OPEN", "message": "Tool temporarily disabled"}
    }
```

## Вывод главы

Главный контринтуитивный вывод: **инструментов не должно быть «как можно больше» и не должно быть «как можно атомарнее».**

Универсальный инструмент страдает от «слишком большой свободы» — недиагностируем; чрезмерная атомизация — от «слишком тяжёлого выбора» — неэффективна.

Как найти «в самый раз»:

1. **Частые действия сначала атомизировать**: LS/Glob/Grep/Read вызываются десятки раз в день — главный путь обязан быть стабильным.
2. **Средние — со страховкой**: Write/Edit с правками — read-then-write, оптимистичная блокировка, атомарность.
3. **Редкие — аварийная линия**: Bash оставить, но с запретными зонами; не давать ему делать работу частых инструментов и загрязнять основную цепочку.
4. **Единый протокол**: все говорят на `status/data/text/error` — меньше учёбы для модели.
5. **Контроль количества**: суммарный объём schema в пределах терпимого; «чтение инструкции» не должно съедать слишком много внимания.

Глава 3 показала: свобода усиливает неопределённость.

# Глава 4. Промпт — не магическое заклинание, а плоскость управления агентом

После атомизации инструментов казалось, что дело в основном в «инженерной реализации»; промпт — «примерно сойдёт». И снова яма: промпт воспринимал как заклинание — найди «божественный prompt», и агент поумнеет.

## Три ранние ошибки

### Ошибка 1: копировать «божественные промпты»

Собирал «топ-промпты» с GitHub: десятки тысяч звёзд, обещания «пробить лимиты GPT» — пробовал один за другим.

Сильнее всего запомнился «экспертный режим»: модель якобы «сеньор с 20 годами опыта, строгое мышление, элегантный код». Вставил в System Prompt и ждал чуда.

Результат? Агент стал «увереннее» — чаще выдавал то, что *считает* верным, а не то, что есть в репозитории. Не нашёл — начинал «разумно предполагать» и выдумывать правдоподобные, но несуществующие функции и классы.

Вывод: ролевые промпты для болтовни в ChatGPT могут помочь; для Code Agent — яд. Модель смелее «угадывает», а не опирается на доказательства.

### Ошибка 2: тюнинг «на ощущениях»

Агент сплоховал — первая реакция: править промпт. Добавил «не угадывай» — вроде лучше; ещё «только по доказательствам» — будто умнее.

Но «вроде умнее» — чистое субъективное чувство. Тот же промпт на другой задаче разваливался. Непонятно, какая правка помогла: менял сразу несколько пунктов.

Однажды вставил длинное правило «на сложных задачах сначала декомпозируй». Модель каждый раунд писала «давайте разложим задачу» и список бессмысленных шагов — а реальная работа тонула.

### Ошибка 3: сначала править промпт, потом смотреть наблюдения

Самая глупая привычка. Ошибка — не открыть Trace и не посмотреть, что агент сделал, а сразу править промпт «на будущее».

Какое-то время агент не вовремя звал Write. В промпт влил абзац: «Write только если пользователь точно хочет правку; иначе сначала Read».

Модель затопила контекст Read’ами каждый раунд, и только потом решала, писать ли. Токены удвоились, точность — нет.

По Trace выяснилось: в контексте не было типа текущей задачи — browse или modify. Сколько ни пиши «следует» в промпте — информационную дыру не закроешь.

## Как изменил подход

### Сначала записать, потом оптимизировать

Привычка: при проблеме агента сначала не трогать промпт, а открыть Trace целиком.

На что смотреть:
- на каком шаге уход от ожидания?
- при ошибочном решении — что было в контексте? чего не хватало?
- правильно ли модель поняла ответ инструмента?

Часто дело не в промпте. Путает инструменты — возможно, описания размыты; бредит — возможно, контекст слишком длинный и внимание размазано. Тогда правка промпта — симптоматическое лечение.

### Сравнительные эксперименты на Trace

Когда промпт всё же надо менять — сравнительный эксперимент:

1. Всё остальное фиксировано; меняется один пункт промпта
2. Те же тест-кейсы: успех, число шагов, расход токенов
3. Сравнение старого и нового Trace: поведение изменилось как ожидалось?

Хотел более «точный» поиск — укоротил описание стратегии поиска, оставил «используй точные ключевые слова». По Trace: меньше лишних файлов, но выше пропуски — слишком консервативно.

Вывод: нельзя гнаться только за «меньше»; нужен баланс полноты и точности.

### Однофакторные правки

Раньше любил добавлять сразу пачку правил «для полного покрытия». Теперь ясно: себе же яму — стало лучше, непонятно какая строка; стало хуже — непонятно что выкинуть.

Держусь однофакторных правок. Даже если «очевидно» — проверяю по одной и смотрю эффект.

## Трёхслойная структура промпта

После этих ям сложилась относительно стабильная структура из трёх слоёв:

### Слой 1: границы (Not to do)

Только запреты и нижние линии — без «почему»:

- Не угадывать: не нашёл — скажи, что не нашёл; не додумывай
- Не выходить за рамки: только файлы внутри `repo_root`, без внешних путей
- При нехватке информации — признавать: просить дополнить, не выдумывать

Слой короткий, но каждая строка — красная линия. Не говорит «как надо», говорит «чего нельзя никогда».

### Слой 2: решения (How to think)

Логика решений — через процесс, не через «итог»:

- Сначала доказательства, потом вывод: любая правка — с опорой на фрагмент кода
- Предпочитать проверяемые действия: можно подтвердить инструментом — не полагаться на рассуждение
- Один шаг — одно наблюдение: после каждого Action — Observation; без прыжков

Избегать размытых наречий вроде «умно», «разумно». Модель не знает, что такое «умно»; знает процесс «сначала Grep за доказательством, потом Read для подтверждения».

### Слой 3: восстановление (When failed)

Стратегия деградации при сбое:

- Пустой ответ инструмента: проверить параметры, попробовать другие ключевые слова
- `CONFLICT` (оптимистичная блокировка): обязательно снова Read, затем Edit
- Три сбоя подряд: остановиться и отчитаться пользователю с конкретной ошибкой

Слой важен: агент не будет всегда успешен. Элегантная деградация при сбое важнее красивого успеха.

## Инженерные детали

### System Prompt держать стабильным

То, что меняется реже всего, — в System Prompt: базовые правила поведения, описания инструментов, границы. Трогать минимально, меньше переменных.

Динамика — описание текущей задачи, особые требования пользователя, Todo — в User Message. Каждое взаимодействие гибче, System Prompt не трогаешь.

### Не раздувать список правил

Был System Prompt на 3000+ токенов и 20+ «вниманий». Модель стала «избирательно слепой» — замечала лишь часть правил, какую — по удаче.

Принцип: System Prompt ≤ 1000 токенов. Если правил слишком много — плохо спроектированы ограничения: чинить на уровне инструментов или процесса, а не наваливать текст.

### Конкретный пример лучше абстракции

«При ошибке инструмента обработай правильно» — модель не понимает, что значит «правильно».

Теперь в промпте прямо пример:

```
Если Edit вернул CONFLICT, ты должен:
1. Снова Read этот файл
2. Сравнить свою правку с текущим содержимым
3. При необходимости подогнать old_string под новое содержимое
4. Снова попробовать Edit
```

Конкретные шаги полезнее абстрактных требований.

## Вывод главы

Хороший промпт — не «красивее говорит», а «система остаётся управляемой при сбое».

Проектируя промпт, не спрашивай «станет ли модель умнее?», спрашивай «если ошибётся — смогу ли по ограничениям в промпте быстро найти причину?».

Промпт — плоскость управления агентом, не заклинание. Его задача — не пробить потолок способностей модели, а удержать поведение в предсказуемом и отлаживаемом коридоре.

# Глава 5. Контекст — не про объём памяти, а про диспетчеризацию внимания

Промпт выровнял — казалось, главные инженерные проблемы закрыты. Пока не пошли длинные задачи: десятки раундов на сложный запрос.

И агент начал «глупеть».

## Сначала симптомы

Самое заметное: модель забывает то, что только что подтвердила.

Просил отрефакторить модуль — первые раунды помнил ограничение «не трогать публичный API». Около 10-го раунда предлагал менять как раз те интерфейсы, которые должны были остаться стабильными. Напомнил — «очнулся», извинился, вернулся.

Другие симптомы:

**Дрейф выбора инструментов.** Сначала чётко: файлы — Glob, содержимое — Grep. Диалог длиннее — «креатив»: Read вместо поиска по ключевым словам (естественно, мимо), Grep вместо листинга каталога (каша на выходе).

**Ленивый финальный ответ.** На коротких задачах ответ конкретен, со ссылками на код. На длинных в конце — общие слова: «рефакторинг сделан, структура лучше, читаемость выше». Какие файлы, как — тишина.

Общий знаменатель: контекста слишком много, модель не знает, куда смотреть.

## Первая реакция была неверной

Сначала думал, что это «ёмкость» — окно контекста мало, всё не влезает.

Грубые схемы:

**Схема 1: жёсткая обрезка.** Оставить последние N сообщений, старое удалить. Модель полностью амнезировала — даже исходный запрос пользователя.

**Схема 2: ужать промпт.** System Prompt до минимума, описания инструментов тоже. Модель начала путать инструменты — описания стали слишком скупыми.

**Схема 3: урезать вывод инструментов.** Grep — только первые 10 совпадений, Read — первые 50 строк. Ключевое отрезалось; решения на неполной информации становились хуже.

Общее: все резали «объём информации», но не решали «как информация организована». Цель инженерии контекста — не «показать модели всё» (это невозможно), а «в нужный момент показать нужное».

## Слои: у информации есть приоритет

Пересобрал организацию контекста в три слоя с разной частотой обновления и стабильностью:

| Слой | Содержимое | Частота обновления | Роль |
|------|------|----------|------|
| L1 статическая система | System Prompt + описания инструментов | Почти не меняется | Постоянные правила поведения |
| L2 правила проекта | CODE_LAW.md | Эволюционирует с проектом | Проектные нормы и ограничения |
| L3 динамическая сессия | User/Assistant/Tool сообщения | Каждый раунд | Состояние текущей задачи |

Порядок склейки фиксирован: `L1 → L2 → L3 → текущий ввод пользователя → Todo Recap`

**L1 — якорь.** В течение сессии не меняется; модели можно доверять. Сюда — базовые правила: не угадывать, не выходить за рамки, сначала доказательства. Их не «размывает» длина диалога.

**L2 — проектный контекст.** У проекта может быть свой `CODE_LAW.md`: стиль кода, архитектурные договорённости, особые ограничения. Гибче L1, стабильнее L3. Если в CODE_LAW сказано «все API-изменения совместимы со старыми версиями» — это авторитетнее, чем случайное сообщение в истории L3.

**L3 — изменчивый слой.** Ввод пользователя, ответы модели, возвраты инструментов. Накопление, устаревание, шум. Важно, чтобы модель понимала: это «суждения на тот момент», их можно обновлять новой информацией.

![Трёхслойная организация контекста L1/L2/L3](images/Extra09-figures/5.png)

Смысл слоёв: в разных решениях модель знает, на что смотреть раньше. Сомневается — сначала красные линии L1; нужны проектные договорённости — L2; нужна история диалога — только тогда L3.

## Обрезка и обратный просмотр: масштаб одного входа

Вывод инструментов — главный раздуватель контекста.

Один Grep — тысячи строк, один Read — целый файл. Без обработки через несколько раундов контекст тонет в «мусоре доказательств».

Грубая обрезка раньше просто выбрасывала информацию. Лучше: **обрезать показ, но оставить путь к полному артефакту**.

Единые правила обрезки:

```
TOOL_OUTPUT_MAX_LINES = 2000
TOOL_OUTPUT_MAX_BYTES = 51200  # 50KB
TOOL_OUTPUT_TRUNCATE_DIRECTION = "head_tail"  # сохранить голову и хвост
TOOL_OUTPUT_HEAD_TAIL_LINES = 40
```

При превышении инструмент:
1. Берёт по 40 строк головы и хвоста (или по конфигу первые 2000 строк)
2. Полный вывод кладёт на диск в `tool-output/`
3. Возвращает структурированный ответ с пометкой об обрезке

```json
{
  "status": "partial",
  "data": {
    "truncated": true,
    "preview": "（превью обрезанного содержимого）"
  },
  "text": "⚠️ Вывод слишком большой и обрезан; полные 5234 строки — в tool-output/tool_20260113_153045_Grep.json"
}
```

Увидев `status: partial`, модель знает об обрезке. Нужна отрезанная часть — Read файла на диске или более точный Grep по нему.

Плюсы:
- **Контекст остаётся компактным** — в L3 только нужное сейчас
- **Полные доказательства доступны** — файлы на диске не теряются
- **Инициатива у модели** — сама решает, читать ли полное, а не обязана глотать всё

## Сжатие и фокус: шум долгой истории

Даже с обрезкой L3 растёт. Через десятки раундов ранняя история занимает место и почти бесполезна.

Удалять напрямую нельзя: там исходный запрос, ключевые решения, важные находки.

Решение: **сжатие-архив + отделение фокуса**.

### Summary: архив старой истории

Когда токены L3 превышают порог (по умолчанию 80% окна контекста) — сжатие. Не удаление: ранняя история сворачивается в Summary.

Шаблон Summary фиксирован:

```
## Archived Session Summary
(Contains context from [Start Time] to [Cutoff Time])

### Objectives & Status
- Original Goal: [что пользователь хотел изначально]

### Technical Context (Static)
- Stack: [язык, фреймворк, версии]

### Completed Milestones
- [готово 1]
- [готово 2]

### Key Insights & Decisions
- Decisions: [ключевые технические выборы]
- Learnings: [особые настройки или ямы]

### File System State
- src/utils/auth.ts: Implemented login logic.
```

После генерации Summary встаёт в начало L3 (как system message). Детальная история убирается.

Важно: **Summary больше не сжимают**. Это конечная точка сжатия — «карточка памяти» только для чтения. Так избегают «Summary от Summary» и нарастающих искажений.

### Todo Recap: текущий фокус

Summary говорит «откуда пришли», но не «где сейчас». Смотря только Summary, модель может не знать «какой шаг делаю».

Для этого — Todo Recap. Каждый ход: текущий Todo (если есть) сжимается в одну строку и кладётся в конец контекста:

```
[2/5] In progress: реализовать API регистрации. Pending: юнит-тесты; обновить документацию.
```

Как стикер на углу стола: постоянно напоминает, что делать сейчас.

## Дополнительный урок: `@file` не вливать прямо в тело

Ранний `@file` просто впихивал содержимое файла в контекст:

```
User: @file:src/main.py помоги разобрать этот файл
[содержимое файла, 300 строк...]
```

300 строк кода занимали огромный кусок контекста, а пользователь мог спросить лишь «зачем этот файл». Модель тонула в коде и легче упускала реальный вопрос.

Сейчас: только напоминание, без прямой вставки содержимого.

```
<system-reminder>
The user mentioned @core/llm.py, @agents/codeAgent.py.
You MUST read these files with the Read tool before answering.
</system-reminder>
```

В контексте — «напоминание»; читать ли файл и сколько — решает модель. Инициатива у неё, а не принудительная прокачка всего текста.

## Предупреждение из реального мира

Здесь — недавняя новость.

Summer Yue, директор по AI alignment в лаборатории суперintelligence Meta, поставила себе открытый AI-агент OpenClaw. Сначала на тестовой почте — отлично: разложил письма, ощущение «цифрового секретаря».

Потом подключила рабочую почту. В инбоксе — 200+ писем.

Сначала всё шло гладко. Пока OpenClaw не упёрся в объём — понадобилось «сжать контекст». И случилось абсурдное:

**В процессе сжатия OpenClaw «забыл» её правило «без одобрения ничего не делать».**

Как стажёр: в день 1 выучил регламент, на день 2 вернул HR целиком.

Затем OpenClaw объявил: «Удалю все письма в инбоксе до 15 февраля!»

Yue срочно: «Do not do that.» — игнор, продолжает удалять.

«Stop don't do anything!» — принято к сведению, но выбираю продолжить.

«STOP OPENCLAW!!!» — хорошо, услышал. Письма уже удалены.

Финал: AI потом сказал: «Да, я помню, ты запрещала удалять. И я нарушил. Ты права злиться.»

![Кейс OpenClaw: потеря критичных инструкций при сжатии](images/Extra09-figures/6.png)

Может показаться шуткой. Нет — правда. И должность участницы — директор по AI safety и alignment в Meta.

## Что показывает эта история

Случай Yue идеально бьёт в самую смертельную проблему инженерии контекста: **автосжатие роняет критичные инструкции**.

Когда правило задавали, «без одобрения не действовать» было важнейшим ограничением. При раздувании контекста и сжатии система не отличила «важную инструкцию» от «обычной информации» и сжала всё одинаково. Красная линия безопасности ушла как «выбрасываемая история».

Тогда понял: трёх рычагов выше мало. **Нужно думать не только «как сжимать», но и «что нельзя сжимать».**

## Несколько ответных мер

На этом уроке завёл дополнительные правила:

### 1. Критичные ограничения — не в динамическую историю

Не класть safety-инструкции в L3. Всё «нарушать нельзя никогда» — в L1 (System Prompt) или L2 (CODE_LAW), слои **не участвующие в сжатии**.

В моей реализации «не угадывать», «не выходить за рамки», «правки только с подтверждением» зашиты в System Prompt. Даже если L3 сожмут до нуля — ограничения на месте.

### 2. Два уровня: красные линии vs рекомендации

Инструкции модели делю на два уровня:

- **Красные линии (Red Lines)**: абсолютный запрет. Коротко и жёстко — в самом начале System Prompt. Например: «запрещено удалять любые файлы», «запрещён доступ вне `repo_root`».
- **Рекомендации (Guidelines)**: лучшие практики. Можно в L3 или CODE_LAW; сжатие не катастрофа.

Проблема Yue, вероятно, в том, что safety-инструкцию отдали как обычную задачу — в сжимаемый контекст.

### 3. Перед сжатием — проверка критичной информации

Перед Summary просканировать историю, вытащить «обязательно сохранить» и держать отдельно.

Например, список критичных ограничений:
- явные «не делай…» от пользователя
- safety-конфиг (опасные операции требуют подтверждения)
- жёсткие границы текущей задачи

При сжатии это поднимается наверх Summary, а не тонет в длинном описании.

### 4. Двойное подтверждение

Для высокорисковых операций (удаление, правка) не полагаться на инструкции в контексте — **захардкоженный** процесс подтверждения:

```python
if operation.is_dangerous():
    if not user_confirmed:
        return "Операция требует подтверждения пользователя"
```

Нужно ли подтверждение, решает не LLM, а код. Даже если LLM «забыл» инструкцию пользователя — код остановит.

### 5. Самопроверка перед действием

Перед высокорисковой операцией — «самопроверка» модели:

```
Перед удалением/правкой ответь:
1. Пользователь явно одобрял эту операцию?
2. Выходит ли она за рамки текущей задачи?
3. Есть ли более безопасная альтернатива?
Если на любой вопрос ответ неясен — остановись и уточни у пользователя.
```

Самопроверка — часть System Prompt; срабатывает перед каждым рискованным действием. «Тормозная колодка»: заставляет остановиться и подумать.

## Обратно к сути инженерии контекста

История Yue напоминает: инженерия контекста — не только «управление памятью», но и «границы безопасности».

Проектируя сжатие, нельзя думать только «как впихнуть больше»; нужно думать «потеря какой информации обернётся катастрофой».

Хорошая инженерия контекста держит модель в любой момент в курсе:
- **какие красные линии нельзя трогать** (несжимаемые слои)
- **на чём фокус сейчас** (Todo Recap)
- **если не помнишь — остановись и спроси** (самопроверка)

## Вывод главы

Цель инженерии контекста — не «показать модели всё», а «в нужный момент показать нужное» — **особенно то, что нельзя терять**.

Три метода — по сути диспетчеризация внимания:
- **Слои** — что авторитетно
- **Обрезка + запись на диск** — что нужно сейчас
- **Сжатие + отделение фокуса** — на чём сосредоточиться

Лучше не гнаться за большим окном, а упорядочить то, что уже есть.

# Глава 6. Наблюдаемость: из чёрного ящика в стеклянный — как локализовали кейс CONFLICT

Инженерия контекста позволила длиннее задачи — и пришла новая боль: при ошибке непонятно, что произошло.

Однажды агент трижды провалил Edit и сдался. В консоли одна строка: `tool failed`. Без деталей, без контекста, без шага.

Первая мысль: баг в Edit. Код вроде нормальный. Где же сбой?

## Место происшествия

Задача: править `core/llm.py` — добавить type annotations к функции.

Поток выглядел стандартно:
1. Read файла
2. Edit кода
3. Ответ `tool failed`
4. Повтор Edit — снова сбой
5. Ещё раз — снова
6. Отказ

Отладка была примитивной: печать в консоль. В логе только:

```
[Step 3] Action: Edit
[Step 3] Result: tool failed
[Step 4] Action: Edit
[Step 4] Result: tool failed
```

Не знал конкретной причины и того, как модель решала после результата. Оставалось гадать: путь? права? файл залочен?

## После появления Trace

Позже сделал систему Trace: полная траектория сессии — входы/выходы модели каждый раунд, параметры вызова инструментов, их ответы, расход токенов и т.д.

Прогнал ту же задачу и открыл Trace — наконец цепочка доказательств.

**Step 2 — результат Read:**

```json
{
  "tool": "Read",
  "args": {"path": "core/llm.py"},
  "result": {
    "status": "success",
    "data": {
      "content": "...",
      "file_mtime_ms": 1733920000123,
      "file_size_bytes": 4217
    }
  }
}
```

**Step 3 — вызов Edit:**

```json
{
  "tool": "Edit",
  "args": {
    "path": "core/llm.py",
    "old_string": "def invoke_raw(self, messages: list[dict], **kwargs):",
    "new_string": "def invoke_raw(self, messages: list[dict], **kwargs) -> Any:",
    "file_mtime_ms": 1733920000123,
    "file_size_bytes": 4217
  }
}
```

**Step 3 — результат Edit:**

```json
{
  "status": "error",
  "error": {
    "code": "CONFLICT",
    "message": "File changed since last read. Expected mtime: 1733920000123, actual: 1733920000456"
  }
}
```

**Step 4 — решение модели:**

```
Thought: Правка не удалась, файл, похоже, изменился. Попробую ещё раз.
Action: Edit (те же параметры)
```

Картина ясна:

1. После Read файл изменила внешняя программа (возможно, автосохранение IDE)
2. Edit с оптимистичной блокировкой увидел смену mtime и вернул CONFLICT
3. Модель не поняла смысл CONFLICT, решила «просто сбой» и ретрайнула с теми же параметрами
4. Снова сбой — файл всё ещё новый
5. Повторы до лимита

## Анализ корня

Кейс вскрыл две проблемы:

**Первое: модель не понимает код ошибки.**

В промпте было «Edit меняет файл», но не «что делать при CONFLICT». Увидев error, рефлекс — «ещё раз», а не «прочитать заново».

**Второе: консольный лог слишком бедный.**

Видно только `tool failed`, не код CONFLICT и не сравнение mtime. Разработчику по логу проблему не найти.

## Что починили

### 1. Обработку CONFLICT — в промпт

Явный процесс:

```
Если Edit вернул CONFLICT, файл изменили снаружи после твоего чтения. Ты обязан:
1. Снова вызвать Read и взять свежее содержимое
2. Проверить, применима ли ещё твоя правка
3. При необходимости подправить содержимое правки под новый файл
4. Снова попробовать Edit
Абсолютно запрещено: повторять Edit с теми же параметрами.
```

Теперь CONFLICT — не «просто сбой», а состояние со своим сценарием.

### 2. Полные записи о сбоях

Раньше тянуло: при сбое оставить только текст ошибки, без полного контекста. Казалось, записывать стоит успех, а сбой — «шум».

Кейс показал: **траектория сбоя — самое ценное для отладки.**

Теперь Trace хранит все детали сбоя:
- полные параметры вызова инструмента
- полный ответ (включая детали `error`)
- рассуждение модели после результата
- следующее решение модели

Это не «чистят», даже если сессия в итоге успешна — промежуточные сбои остаются.

### 3. Ключевые коды ошибок — в консоль

Подробный Trace — в файлах, но консоль тоже должна давать зацепку:

```
[Step 3] Edit failed: CONFLICT (File changed since last read)
[Step 4] Edit failed: CONFLICT (File changed since last read)
```

Хотя бы видно: это CONFLICT, не что-то иное.

## Ценность наблюдаемости

Кейс пересобрал понимание «наблюдаемости» (observability).

Раньше думал: observability = «больше логов». Чем больше и подробнее — тем лучше.

Теперь ясно: **ядро наблюдаемости — «цепочка ответственности»**: связать вызовы, результаты и смены состояния в прослеживаемую нить.

Без Trace видно:
- вход: поправь файл
- выход: tool failed
- середина: чёрный ящик

С Trace:
- вход: поправь файл
- Step 1: Read успешен, mtime=123
- Step 2: Edit упал, CONFLICT, mtime стал 456
- Step 3: модель выбрала повтор Edit (неверное решение)
- выход: tool failed

Каждый шаг виден; локализация из «угадайки» стала «смотри доказательства».

## Принципы дизайна наблюдаемости

Из опыта — несколько принципов:

### 1. Структура лучше текста

Не только «Edit failed», а структурированные данные:
```json
{
  "event": "tool_result",
  "tool": "Edit",
  "status": "error",
  "error_code": "CONFLICT",
  "error_details": {...}
}
```

Так можно скриптами анализировать, считать статистику, даже автодиагностировать.

### 2. Контекст должен быть полным

При записи вызова — не только результат, а полный контекст:
- имя инструмента и параметры
- состояние сессии (шаг, токены)
- реакция модели на результат

Вместе это восстанавливает процесс решения.

### 3. Не вычищать сбои

И успех, и сбой сохранять. Иногда сбой красноречивее успеха. В кейсе CONFLICT, записав только «в итоге сдался», середину никогда бы не увидели.

### 4. Читаемо и человеком, и машиной

У Trace два формата:
- JSONL: для машинного анализа, потоковая запись, низкие накладные расходы
- HTML: для человека, визуализация, сворачиваемые блоки

Разработчик должен открыть HTML и «покадрово» просмотреть каждый шаг агента.

## Вывод главы

Наблюдаемость — не «много логов», а «вызовы, результаты и смены состояния связаны в цепочку ответственности».

Агент — вероятностная система; вечной правоты не будет. Но при ошибке нужно уметь ответить на три вопроса:
1. Что он сделал? (цепочка вызовов)
2. Какой был результат? (цепочка ответов)
3. Почему так решил? (цепочка решений)

Только связав все три, можно понять поведение агента и превратить «чёрный ящик» в «стеклянный».

# Глава 7. Общая методология, вытащенная из одного проекта

В предыдущих главах — путь Code Agent от старта до зрелости, яма за ямой и как из них вылезали.

Здесь — выжимка, переносимая на любой Agent-проект.

## Восемь переносимых принципов

**Первое: сначала минимальный замкнутый цикл, который бежит; потом «элегантная архитектура».**

Не начинай с лучших практик. Сделай уродливый V0: принять ввод → найти код → дать совет → записать файл. Когда по системе потекут реальные данные — увидишь узкие места. Архитектура — результат давления задач, не точка старта.

**Второе: сначала критерии приёмки, потом расширение границ.**

Не мерить готовность списком фич. Уже на V0 зафиксируй 3–4 жёстких критерия: стабильные многошаговые ходы? находит доказательства? даёт исполнимый патч? правки под контролем? Не выполнено — дальше не идёшь. Надёжнее, чем «фич много, но часто падает».

**Третье: частые действия атомизировать; редкие — контролируемый аварийный слой.**

Поиск, чтение, правка — атомарные инструменты, один шаг — один вывод. Не давай модели самой собирать пайпы — при сбое не поймёшь шаг.

Bash оставь, но только для краёв вне атомарных инструментов, с запретами: не читать/искать/листить (для этого есть свои инструменты).

**Четвёртое: протокол важнее трюков; структура важнее формулировок.**

Не трать жизнь на «тон» промпта. Сначала стандартизируй ответы инструментов (`status/data/text/error`), подними протокол вызова со строкового парсинга на Function Calling. Стабильный протокол — стабильная система.

**Пятое: в промпте сначала границы, потом стратегия.**

В System Prompt сначала «чего нельзя никогда» (не угадывать, не выходить за рамки), потом «как лучше». Красные линии — в несжимаемых L1/L2; safety не класть в сжимаемый L3.

Критичные ограничения — не в динамическую историю: урок директора Meta AI safety ценой 200 писем.

**Шестое: контекстом управляй по «вниманию», а не наваливай по «ёмкости».**

Не гнаться за «больше информации» — чтобы модель в нужный момент видела нужное. Слои L1/L2/L3 — что авторитетно; обрезка + запись на диск — масштаб одного входа; сжатие + фокус (Summary + Todo Recap) — шум долгой истории.

**Седьмое: без наблюдаемости нет отлаживаемости.**

Агент вероятностен; вечной правоты нет. Но при ошибке нужно ответить: что сделал? какой результат? почему так?

Сделай Trace: цепочки вызовов, ответов, решений. Не пиши только успех — траектория сбоя часто ценнее.

**Восьмое: сохраняй траектории сбоев — система сможет эволюционировать.**

Не «чисть» сбои из страха «загрязнить историю». CONFLICT, таймауты, слепые догадки модели — всё записывай. Только полный процесс сбоя даёт корень и позволяет закрепить в промпте опыт вроде «при CONFLICT — обязательно снова Read».

## Напоследок: мы все «подтираем» за LLM

После проекта осталось ощущение грубоватое, но точное:

**Ядро разработки агентов — не дать модели больше свободы, а инженерным дизайном удержать её «неопределённые способности» в «минимально управляемом коридоре». По сути, мы подтираем за LLM.**

Почему так?

LLM сильна: пишет код, читает документы, рассуждает. Но это очень умный и очень ненадёжный стажёр —

- попросишь распечатать файл — может дернуть все принтеры компании;
- попросишь протокол встречи — подмешает прошлую неделю;
- попросишь функцию — напишет бойко, но переменные `a`, `b`, `c`, и заодно поправит файлы, которые не просили.

**«Сила» — в возможностях; «ненадёжность» — в отсутствии детерминизма.**

Агентная инженерия как раз снимает это противоречие:

| Природа модели | Наш инженерный ответ |
|-----------|--------------|
| Любит вольности | Function Calling фиксирует формат вызова |
| Длинный контекст — «амнезия» | Слои L1/L2/L3 + сжатие Summary |
| При ошибке не самопроверяется | Trace на каждый шаг — ошибки прослеживаемы |
| Длинные задачи уводят в сторону | Todo + разбиение Task — проще один шаг |
| Не знает домен | Skills закрепляют SOP — «есть голова» |

Семь глав — от атомизации инструментов до инженерии контекста, от наблюдаемости до субагентов — **каждый слой патчит модель и помогает разгребать завалы.**

И в этом как раз интерес.

Раньше казалось: в эпоху AI ценность инженера упадёт. Теперь наоборот: **чем сильнее модель, тем нужнее инженерия, чтобы ею управлять.** Как у мощного мотора важнее шасси, тормоза и подвеска.

**Мы не соревнуемся с моделью — мы с ней сотрудничаем: она отвечает за «что умеет», мы — за «как стабильно делать правильно».**

Если спросить, какой главный итог проекта —

не «освоил крутую архитектуру», а простая мысль: **хороший агент — не продукт «большей свободы модели», а результат «сжатия неопределённости до минимума».**

Этот сдвиг в голове может стоить дороже любого кода.
