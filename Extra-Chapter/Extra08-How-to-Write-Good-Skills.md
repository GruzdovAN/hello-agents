## 1. Что такое Skill?

### 1.1 Определение

Skill — это папка с инструкциями, справочными материалами, исполняемыми скриптами и другими ресурсами. Когда ИИ получает её, он может выполнять конкретную работу, которую раньше не умел.

Например, в папке навыка `pdf-editor` могут быть инструкция «как обрабатывать PDF», Python-скрипт для поворота PDF и справочник по API — ИИ не нужно ничего искать снаружи: всё уже внутри этой папки.

Понятие не привязано к одному продукту. Codex, Claude или другой ИИ-агент (Agent) — суть skill одна и та же. Можно думать о нём как о **плагине возможностей** для ИИ: подключили — у ИИ появилась специализация; отключили — снова обычный универсальный помощник.

### 1.2 Минимальная форма

Минимум для skill — один файл:

```
my-skill/
└── SKILL.md
```

Структура `SKILL.md` простая: верхняя часть говорит ИИ «когда меня использовать», нижняя — «как именно делать»:

```yaml
---
name: my-skill                    # ← верхняя часть: метаданные
description: >-                   #    по ним ИИ решает, активировать ли навык
  Когда пользователю нужно сделать что-то конкретное, используй этот навык.
---

Нижняя часть: операционные инструкции                   # ← ИИ читает это только после активации
Выполняй по следующим шагам...
```

Верхняя часть называется **frontmatter** (YAML между `---`) и содержит поля `name` и `description`. В начале каждого диалога ИИ сканирует frontmatter всех установленных навыков и по `description` решает: «связан ли этот навык с текущим запросом» — это **единственный** критерий срабатывания.

Нижняя часть — **body** (тело в Markdown): операционные инструкции, которые загружаются только после активации. Если навык не сработал, ИИ сюда никогда не заглянет.

### 1.3 Полная структура

Когда навык усложняется, одного `SKILL.md` недостаточно.

Допустим, навык «обработка PDF»: в `SKILL.md` описан процесс, но код поворота PDF каждый раз один и тот же — заново писать его через ИИ и долго, и рискованно ошибиться. Лучше положить готовый Python-скрипт. Или навык «генератор фронтенд-проекта»: каждый раз нужны одни и те же HTML/React-шаблоны — лучше положить каталог шаблонов и дать ИИ скопировать и править.

Полный каталог skill может выглядеть так:

```
skill-name/
├── SKILL.md                  # [обязательно] точка входа: frontmatter + body
├── agents/
│   └── openai.yaml           # [рекомендуется] «визитка» навыка
├── scripts/                  # [опционально] исполняемые скрипты
├── references/               # [опционально] справочные документы
└── assets/                   # [опционально] шаблоны для результата
```

По пунктам:

- **SKILL.md** — единственный обязательный файл; о нём уже сказано выше

- **scripts/** — готовые программы: ИИ не обязан их понимать, достаточно вызвать через shell. Например, `scripts/rotate_pdf.py`: достаточно выполнить `python rotate_pdf.py input.pdf 90`, чтобы повернуть PDF, без переписывания логики каждый раз. Подходит для операций, где **результат должен быть точным и ИИ нельзя «импровизировать»**

- **references/** — справочники, которые ИИ читает по ходу работы. Например, навык «запросы к BigQuery»: нужно знать таблицы компании и их поля — это кладут в `references/schema.md` и читают по необходимости. Отличие от scripts: references ИИ **читает**, scripts — **исполняет**

- **assets/** — не для чтения ИИ, а файлы, которые сразу идут в итоговый результат. Например, навык «генератор фронтенд-проекта»: в `assets/frontend-template/` лежит набор HTML/React-шаблонов; ИИ копирует их и правит. Или `assets/logo.png` — логотип компании, который ИИ подставляет в страницу. Картинку логотипа не нужно «понимать» — нужно знать, где она лежит и когда её вставить

- **agents/openai.yaml** — «визитка» навыка. Многие продукты показывают список навыков для выбора или поиска. В файле — отображаемое имя, краткое описание, иконка и т.п. На поведение ИИ это не влияет: только для UI продукта

## 2. Вы пишете инструкции для человека или для ИИ?

Зная, что такое skill, можно писать свой. Но у большинства первый skill страдает одной и той же ошибкой.

Пример. Навык «ревью кода» часто пишут так:

```markdown
---
name: code-review
description: Навык ревью кода
---

# Code Review Skill

## Фон
Этот навык обобщает многолетний опыт ревью в команде и призван повышать качество кода и эффективность совместной работы.

## Принципы ревью
- Держать профессиональный, конструктивный тон
- Смотреть на качество кода, а не на личный стиль
- Балансировать строгость и гибкость

## Способ использования
Когда пользователь присылает код, проведи полное ревью и дай предложения по улучшению. Будь дружелюбным и поддерживающим.

## История версий
- v1.0: начальная версия
- v1.1: добавлена поддержка Python
```

Как внутренняя документация для людей это нормально: есть фон, принципы, способ использования и даже история версий.

Но читатель skill — ИИ. С этой точки зрения:

- **«Обобщает многолетний опыт команды»** — ИИ не интересует происхождение навыка, ему нужно знать **что делать сейчас**
- **«Держать профессиональный, конструктивный тон»** — человек уловит настроение, а ИИ развернёт «профессиональный» и «конструктивный» в бесконечные комбинации, и каждый раз вывод будет другим
- **«Балансировать строгость и гибкость»** — опытный ревьюер знает, когда быть жёстким, а когда гибким; у ИИ такой интуиции нет — фраза почти ничего не даёт
- **«Полное ревью и предложения»** — это ожидание от человека; ИИ нужно: что проверить сначала? потом? какие проблемы обязательны? какие можно пропустить?
- **«История версий»** — каждый запуск для ИИ «с нуля»; v1.0 или v1.1 для него не важно
- **description только «Навык ревью кода»** — по description решается срабатывание; пять слов слишком размыты: «посмотри этот код» — срабатывать? «как у функции с производительностью» — срабатывать?

По отдельности ни одна строка не «ошибка», но всё написано для человека. **Проблема не в том, что мало текста, а в том, что неверный адресат.**

Как писать правильно? Готовый ответ — skill-creator у Codex: это «skill для создания skill», и его собственный `SKILL.md` — лучшие практики «как писать инструкции для ИИ».

## 3. Общая рамка skill-creator

Откройте `SKILL.md` у skill-creator (около 370 строк). Прежде чем углубляться в детали, зафиксируем общую картину.

Единственная задача skill-creator: **как в ограниченном окне контекста дать ИИ максимально полезные инструкции?**

Вокруг этого — цельная система проектирования в трёх уровнях.

### Уровень 1: корневое ограничение — краткость

Окно контекста ИИ конечно и общее (системный промпт, история диалога, метаданные всех установленных навыков). Чем больше занимает ваш skill, тем меньше места остаётся остальному. Первый принцип skill-creator: **каждое предложение должно окупать занятые токены (token)**.

### Уровень 2: два измерения проектирования

При ограничении «краткость» при написании skill остаются два ключевых решения:

**Измерение 1: куда класть информацию?**

Не всё нужно загружать сразу. skill-creator задаёт трёхуровневую архитектуру: разная информация попадает в контекст в разное время:

![Стандартная структура Skill и трёхуровневая загрузка](./images/Extra08-figures/skill-structure.png)

- **L1 (метаданные)**: всегда в контексте, ~100 слов — по ним ИИ решает, активировать ли навык
- **L2 (body в SKILL.md)**: загружается после срабатывания, до 5k слов — операционные инструкции
- **L3 (scripts/references/assets)**: по необходимости, без лимита — scripts исполняются без чтения в контекст, стоимость в токенах нулевая

Так решается вопрос «как нести максимум информации минимумом токенов».

**Измерение 2: сколько свободы давать ИИ?**

Не все задачи стоит отдавать на свободный полёт.

Пример: технический блог — десять человек напишут десять стилей, и это нормально: достаточно направления, детали решает ИИ. Это **высокая свобода**.

Генерация YAML-конфига — другое. У `openai.yaml`, который создаёт skill-creator, поле `short_description`: 25–64 символа, первая буква заглавная, без кавычек. 65 символов? Нельзя — UI обрежет. 24? Нельзя — проверка не пройдёт. Без заглавной? Несогласованный вид. Ошибка на один символ ломает результат: свободу ИИ здесь нельзя давать, формат нужно зафиксировать скриптом — это **низкая свобода**. Такие задачи называют «хрупкими операциями»: дело не в сложности, а в том, что **правильно сделать можно одним способом, а ошибиться — сотней**.

![Спектр свободы](./images/Extra08-figures/freedom-spectrum.png)

Так балансируются гибкость ИИ и надёжность результата.

### Уровень 3: процесс внедрения

С принципами и архитектурой skill-creator даёт шестишаговый процесс создания — из идей в исполняемые шаги:

![Шестишаговый процесс создания](./images/Extra08-figures/creation-flow.png)

Понять → спланировать → инициализировать → отредактировать → проверить → итерировать. Скрипты проходят через весь процесс и образуют детерминированную цепочку качества:

![Взаимодействие файлов](./images/Extra08-figures/file-interaction.png)

### Обзор рамки

Связь трёх уровней:

```
Краткость (корневое ограничение)                         → глава 4
 ├── Куда класть информацию? → трёхуровневая архитектура → глава 5
 ├── Сколько свободы ИИ? → спектр свободы и скрипты       → глава 6
 └── Как внедрить? → шестишаговый процесс                 → глава 7
```

Дальше каждая глава раскрывает эту рамку.

## 4. Корневое ограничение: краткость
> Место в рамке: уровень 1

### 4.1 Главное ограничение

Окно контекста ИИ — как рабочий стол: одновременно разложить можно ограниченный объём. На столе уже лежат правила системы, слова пользователя, краткие описания всех установленных навыков. После активации ваш skill тоже занимает место. Стол конечен: чем больше ваша доля, тем меньше остаётся другим.

skill-creator формулирует это первым принципом:

> The context window is a public good. Skills share the context window with everything else Codex needs: system prompt, conversation history, other Skills' metadata, and the actual user request.

Раз место ограничено, как решить, стоит ли класть фрагмент в skill? Исходная гипотеза skill-creator: **ИИ уже умён — добавляйте только то, чего он не знает.**

> Default assumption: Codex is already very smart. Only add context Codex doesn't already have.

Перед каждым абзацем два вопроса:

- «ИИ это уже знает?» — например, «как пишется for-цикл в Python»: знает, учить не нужно
- «Стоит ли этот фрагмент места на столе?» — объяснение на 200 слов можно ли заменить примером кода на 10 строк?

**Практический вывод**: краткий пример вместо длинного объяснения. Хороший пример кода лучше трёх абзацев текста.

### 4.2 Что не класть в Skill?

Skill-creator явно даёт **запретный список**:

> A skill should only contain essential files that directly support its functionality. Do NOT create extraneous documentation or auxiliary files.

Лишние файлы:
- README.md
- INSTALLATION_GUIDE.md
- QUICK_REFERENCE.md
- CHANGELOG.md

> The skill should only contain the information needed for an AI agent to do the job at hand. It should not contain auxiliary context about the process that went into creating it, setup and testing procedures, user-facing documentation, etc. Creating additional documentation files just adds clutter and confusion.

Причина простая: читатель skill — ИИ, не человек-разработчик. Установочные гайды, changelog, quick reference и прочая «документация для людей» не нужны. Каждый лишний файл — шум.

### 4.3 В ограничениях «чего не делать» точнее, чем «что делать»

Краткость — не только «писать меньше», но и «писать верно». Пример.

Когда skill-creator создавал `laotou-thought-style` (навык стиля письма), он **не** писал:

```
Пиши тёплым, сдержанным, проницательным тоном.
```

Позитивное описание кажется ясным, но для ИИ степень «теплоты», баланс «сдержанности» и «проницательности» — сплошная размытость.

Вместо этого — список **антипаттернов** (`references/anti-patterns.md`):

| Не делай так | Симптом | Как исправить |
|-----------|------|--------|
| Нагромождение ролей | Подряд много имён и реплик | Оставь один конфликтный эпизод, добавь абстрактный вывод |
| Только лозунги, без действия | Весь текст «надо держаться, надо стараться» | Замени на маленький шаг, который можно сделать сегодня |
| Сразу мораль | С первых строк — общие законы | Сначала бытовая сцена |
| Слишком резкий финал | Финал «надо меняться!» | Замени на «не спеши», «и так нормально» |
| Чрезмерные абсолюты | «всегда», «обязательно» | Добавь оговорки «чаще всего», «зачастую» |

**Каждый пункт конкретен, проверяем и имеет ясный способ исправления.**

Логика:

```
«Что делать» → описывает бесконечную область допустимого → ИИ случайно блуждает внутри
«Чего не делать» → рисует границы на этой области → пространство поведения сужается до нужного вам
```

Сам skill-creator следует этому: в `SKILL.md` много места уходит на «чего не писать» (What to Not Include in a Skill), а не на расплывчатое «пишите хороший контент».

Закончив `SKILL.md`, сделайте «тест на инверсию»: каждую позитивную подсказку можно ли переписать как «не делай X»? Если да — после переписывания обычно точнее.

### 4.4 Единый повелительный тон

skill-creator требует в body `SKILL.md` единый **повелительный / инфинитивный** тон (Always use imperative/infinitive form). Это не вкус, а снижение неоднозначности: повелительное предложение уже и есть инструкция.

## 5. Измерение проектирования 1: куда класть информацию?
> Место в рамке: уровень 2 — измерение 1

В обзоре рамки в главе 3 уже была трёхуровневая архитектура. Здесь — детали.

### 5.1 Трёхуровневая постепенная загрузка

Определения уровней в оригинале skill-creator:

> 1. **Metadata (name + description)** - Always in context (~100 words)
> 2. **SKILL.md body** - When skill triggers (<5k words)
> 3. **Bundled resources** - As needed by Codex (Unlimited because scripts can be executed without reading into context window)

| Уровень | Содержимое | Когда в контексте | Стоимость в токенах |
|------|------|--------------|-----------|
| **L1** | frontmatter (`name` + `description`) | **всегда** | ~100 слов |
| **L2** | body в SKILL.md | после срабатывания | <5k слов |
| **L3** | scripts/ references/ assets/ | по необходимости | без лимита |

**По сути это система управления информационной энтропией**:

- **L1 — фильтр** — из десятков установленных навыков выбирает нужный сейчас. Неточный description → ложное срабатывание или пропуск
- **L2 — руководство по операциям** — после срабатывания говорит, что делать. Слишком длинный → внимание размывается. Body держите в пределах 500 строк
- **L3 — ящик инструментов** — открывается только когда нужно. Самое эффективное — scripts/: **исполнять, не читая** — нулевая стоимость в токенах

### 5.2 Frontmatter: весь источник механизма срабатывания

В frontmatter обязательны только два поля: `name` и `description`. Но формулировка `description` критична:

> This is the primary triggering mechanism for your skill, and helps Codex understand when to use the skill.

Свой description у skill-creator такой:

```yaml
description: Guide for creating effective skills. This skill should be used when
  users want to create a new skill (or update an existing skill) that extends
  Codex's capabilities with specialized knowledge, workflows, or tool integrations.
```

Он говорит не только «что делает» (creating effective skills), но и «когда использовать» (when users want to create a new skill or update an existing skill).

**Ключевые правила**:
- Всю информацию «when to use» кладите в `description`, **не в body**. Body загружается после срабатывания — к тому моменту Codex уже решил использовать навык, и «когда использовать» уже поздно
- В frontmatter не добавляйте поля кроме `name` и `description` (исключения: `license`, `allowed-tools`, `metadata`)

Пример хорошего description (навык docx):

> "Comprehensive document creation, editing, and analysis with support for tracked changes, comments, formatting preservation, and text extraction. Use when Codex needs to work with professional documents (.docx files) for: (1) Creating new documents, (2) Modifying or editing content, (3) Working with tracked changes, (4) Adding comments, or any other document tasks"

### 5.3 Суть четырёх видов связанных ресурсов

Понять различие этих четырёх ресурсов — ключ ко всей системе skill:

#### Scripts (`scripts/`)

Исполняемый код (Python/Bash и т.д.) для задач, где нужна **детерминированная надёжность** или где код иначе переписывают снова и снова.

- **Когда нужен**: один и тот же код каждый раз пишут заново, или нужен гарантированно надёжный вывод
- **Пример**: `scripts/rotate_pdf.py` для поворота PDF
- **Главный плюс**: экономия токенов, детерминизм, можно исполнять без чтения в окно контекста
- **Замечание**: иногда скрипт всё же нужно прочитать Codex — для правок или адаптации к окружению

#### References (`references/`)

Документы и справочники, которые при необходимости загружают в контекст и помогают Codex рассуждать.

- **Когда нужны**: подробные материалы, на которые Codex опирается в работе
- **Примеры**: `references/finance.md` (финансовая schema), `references/api_docs.md` (спецификация API), `references/policies.md` (политики компании)
- **Назначение**: schema БД, документация API, предметные знания, политики компании, подробные гайды по workflow
- **Главный плюс**: `SKILL.md` остаётся компактным; загрузка только когда Codex считает нужным
- **Лучшая практика**: если файл большой (>10k слов), в `SKILL.md` укажите шаблоны поиска через grep
- **Без дублирования**: информация должна жить **либо** в `SKILL.md`, **либо** в references, не в обоих местах. Детали — в references; в `SKILL.md` — только ядро процесса и навигация по workflow

#### Assets (`assets/`)

Файлы не для загрузки в контекст, а для прямого использования в результате Codex.

- **Когда нужны**: навыку нужны файлы в финальном выводе
- **Примеры**: `assets/logo.png` (бренд), `assets/slides.pptx` (шаблон PPT), `assets/frontend-template/` (HTML/React-шаблон), `assets/font.ttf` (шрифт)
- **Назначение**: шаблоны, картинки, иконки, шаблонный код, шрифты, примеры документов — их копируют или правят
- **Главный плюс**: ресурсы вывода отделены от документации; Codex может их использовать, не читая в контекст

#### Метаданные Agents (`agents/openai.yaml`) (рекомендуется)

Метаданные для UI: не для ИИ, а для фронтенда продукта:

- Поля вроде `display_name`, `short_description`, `default_prompt`
- Генерируются детерминированно скриптом `generate_openai_yaml.py`, а не вручную
- После обновления `SKILL.md` проверьте, что `agents/openai.yaml` ещё соответствует; устарел — перегенерируйте
- Подробные определения полей — в `references/openai_yaml.md`

### 5.4 Три практических паттерна постепенного раскрытия

Skill-creator даёт три конкретных способа выносить содержимое в references:

**Pattern 1: обзор сверху + справочные файлы**

```markdown
# PDF Processing

## Quick start
Extract text with pdfplumber:
[code example]

## Advanced features
- **Form filling**: See [FORMS.md](FORMS.md) for complete guide
- **API reference**: See [REFERENCE.md](REFERENCE.md) for all methods
- **Examples**: See [EXAMPLES.md](EXAMPLES.md) for common patterns
```

Codex загружает FORMS.md, REFERENCE.md или EXAMPLES.md только когда нужно.

**Pattern 2: организация по доменам**

Многодоменный / многовариантный навык: дробление по доменам, чтобы не грузить лишнее:

```
bigquery-skill/
├── SKILL.md (overview and navigation)
└── reference/
    ├── finance.md (revenue, billing metrics)
    ├── sales.md (opportunities, pipeline)
    ├── product.md (API usage, features)
    └── marketing.md (campaigns, attribution)
```

Когда пользователь спрашивает про продажи, Codex читает только `sales.md`.

То же для нескольких фреймворков / вариантов:

```
cloud-deploy/
├── SKILL.md (workflow + provider selection)
└── references/
    ├── aws.md (AWS deployment patterns)
    ├── gcp.md (GCP deployment patterns)
    └── azure.md (Azure deployment patterns)
```

**Pattern 3: условные детали**

Базовое — сразу в тексте; продвинутое — по ссылке:

```markdown
# DOCX Processing

## Creating documents
Use docx-js for new documents. See [DOCX-JS.md](DOCX-JS.md).

## Editing documents
For simple edits, modify the XML directly.

**For tracked changes**: See [REDLINING.md](REDLINING.md)
**For OOXML details**: See [OOXML.md](OOXML.md)
```

### 5.5 Два важных анти-совета

1. **Не делайте глубокую вложенность ссылок** — все reference-файлы должны ссылаться прямо из `SKILL.md`, без цепочки A → B → C
2. **Для длинных файлов — оглавление** — reference длиннее 100 строк: TOC сверху, чтобы Codex сразу видел структуру

### 5.6 Типичные ошибки уровней

| Ошибка | Последствия | Исправление |
|------|------|------|
| Условия срабатывания в body | body грузится после срабатывания — уже поздно | в description frontmatter |
| «When to Use This Skill» в body | то же: Codex уже решил использовать | перенести в description |
| Справочные детали в SKILL.md | body раздувается, плотность падает | вынести в references/, в body — только ссылки |
| Детерминированную операцию — текстом | ИИ каждый раз заново «понимает», возможны ошибки | обернуть в scripts/, исполнять без чтения |
| references ссылаются друг на друга | ИИ ходит по нескольким прыжкам | все references — прямые ссылки из SKILL.md |
| Дублирование SKILL.md и references | трата токенов, риск рассинхрона при обновлении | информация только в одном месте |

## 6. Измерение проектирования 2: сколько свободы давать ИИ?
> Место в рамке: уровень 2 — измерение 2

Зная, куда класть информацию и как её ограничивать, следующий вопрос: **что делает ИИ, а что — скрипт?**

ИИ силён в смысле, генерации текста, творческой работе. Слаб в точном контроле формата, ограничениях длины, правилах именования — в «хрупких операциях».

### 6.1 Три ступени свободы

Skill-creator использует **спектр свободы**, чтобы учесть эту неоднородность (см. схему рамки в главе 3):

> Think of Codex as exploring a path: a narrow bridge with cliffs needs specific guardrails (low freedom), while an open field allows many routes (high freedom).

**Высокая свобода** (текстовые инструкции): много методов допустимы, решение зависит от контекста — ведите эвристиками.

**Средняя свобода** (псевдокод / скрипт с параметрами): есть лучшие практики, но возможны вариации; конфигурация влияет на поведение.

**Низкая свобода** (конкретный скрипт, мало параметров): операция хрупкая, важна согласованность, нужна фиксированная последовательность.

Ядро логики:

```
Чем хрупче задача (легко ошибиться) → тем ниже свобода → фиксировать скриптом
Чем гибче задача (много верных путей) → тем выше свобода → вести текстом
```

### 6.2 Распределение свободы у самого skill-creator

| Задача | Свобода | Способ |
|------|--------|---------|
| Понять запрос пользователя и задать вопросы | высокая | текстовые указания в SKILL.md |
| Спланировать структуру содержимого навыка | средняя | шаблон + рекомендация режимов в форме выбора |
| Инициализировать структуру каталога | **низкая** | скрипт `init_skill.py` |
| Сгенерировать openai.yaml | **низкая** | скрипт `generate_openai_yaml.py` |
| Написать содержимое SKILL.md | высокая | принципы + советы по письму |
| Проверить итоговый результат | **низкая** | скрипт `quick_validate.py` |

### 6.3 Ошибки в обе стороны

**Ошибка 1: слишком много свободы для хрупкой задачи**

```markdown
# Неверно
Сгенерируй файл openai.yaml с полями display_name и short_description.

# Последствия: short_description может превысить лимит 64 символа, регистр может быть несогласован
```

Подход skill-creator: зафиксировать формат скриптом `generate_openai_yaml.py`. ИИ только даёт значения параметров; скрипт гарантирует соответствие.

**Ошибка 2: слишком много ограничений для творческой задачи**

```markdown
# Неверно
Первый абзац обязан начинаться с «вчера», второй — содержать «по сути», последний — заканчиваться на «не спеши».

# Последствия: текст как игра в подстановку слов
```

Подход skill-creator: задать пропорции структуры (слой сцены ≤30%, слой принципа 30–40%), но не фиксировать конкретные слова.

### 6.4 Критерии решения

Два вопроса:
1. **Насколько тяжелы последствия ошибки?** — чем тяжелее → тем ниже свобода
2. **Сколько «правильных» способов?** — чем больше → тем выше свобода

### 6.5 Реализация низкой свободы: три скрипта skill-creator

Поняв спектр свободы, понятно, зачем у skill-creator три скрипта — это конкретная реализация «низкой свободы» (взаимодействие скриптов — на схеме рамки в главе 3).

**`init_skill.py` (гарантия входа, 398 строк)**

Каркас для инициализации каталога нового навыка, аналог `create-react-app` для React-проекта:

```bash
scripts/init_skill.py <skill-name> --path <output-directory> \
  [--resources scripts,references,assets] [--examples] \
  [--interface key=value]
```

Основные возможности:
- создать каталог навыка
- сгенерировать шаблон `SKILL.md` с плейсхолдерами TODO (TODO — «пропуски» для Codex)
- вызвать `generate_openai_yaml.py` для `agents/openai.yaml` (через `--interface key=value` передать сгенерированные ИИ `display_name`, `short_description`, `default_prompt`)
- опционально создать подкаталоги `scripts/`, `references/`, `assets/`
- опционально добавить примеры (`--examples`)
- встроенный `normalize_skill_name()` нормализует произвольный ввод пользователя в hyphen-case

Примеры:

```bash
scripts/init_skill.py my-skill --path skills/public
scripts/init_skill.py my-skill --path skills/public --resources scripts,references
scripts/init_skill.py my-skill --path skills/public --resources scripts --examples
```

**`generate_openai_yaml.py` (гарантия формата, 226 строк)**

Отвечает за создание и обновление `agents/openai.yaml`:

- читает имя навыка из frontmatter `SKILL.md`
- автоматически переводит hyphen-case в Title Case (`my-cool-skill` → `My Cool Skill`)
- встроенные словари аббревиатур (GH, MCP, API и т.д. остаются в верхнем регистре) и брендов (openai → OpenAI)
- автоматически генерирует `short_description` длиной 25–64 символа
- поддерживает переопределение любых полей через `--interface key=value`

```bash
scripts/generate_openai_yaml.py <path/to/skill-folder> --interface key=value
```

**`quick_validate.py` (гарантия выхода, 102 строки)**

«Контролёр качества» после создания навыка:

```bash
scripts/quick_validate.py <path/to/skill-folder>
```

Что проверяет:
- существует ли SKILL.md
- валиден ли формат YAML frontmatter
- `name`: hyphen-case, ≤ 64 символа, без подряд идущих / концевых дефисов
- `description`: есть, без угловых скобок, ≤ 1024 символа
- разрешены только 5 ключей frontmatter: `name`, `description`, `license`, `allowed-tools`, `metadata`

### 6.6 Цепочка обеспечения качества

Три скрипта образуют **детерминированную цепочку гарантий**, сжимая посередине творческий шаг:

```
init_skill.py (гарантия входа)
  нормализация имени + структура каталога + шаблон
  → корректная стартовая точка
       ↓
  творческое написание ИИ (высокая свобода)
  → содержимое SKILL.md, references, свои scripts
       ↓
quick_validate.py (гарантия выхода)
  формат frontmatter + правила имён + ограничения длины
  → корректная конечная точка
```

Ключевой вывод: скрипты «исполняются, не читаясь» — **нулевая стоимость в токенах**. Любую сложную детерминированную логику можно упаковать в скрипт, не боясь за окно контекста. Поэтому skill-creator отдаёт скриптам преобразование имён (словари аббревиатур и брендов), ограничения длины (25–64 символа), проверку формата и прочие мелкие, но хрупкие операции.

### 6.7 Что стоит обернуть в скрипт?

```
Результат каждого запуска должен совпадать      → скрипт
Точный формат / ограничение длины               → скрипт
Преобразование правил именования                → скрипт
Проверка соответствия правилам                  → скрипт
Один и тот же код каждый раз пишут заново       → скрипт

Нужно понимание контекста                       → текстовая инструкция
Несколько разумных подходов                     → текстовая инструкция
Нужно творческое суждение                       → текстовая инструкция
```

Иногда скрипт всё же нужно прочитать Codex (правки или адаптация окружения), но чаще он «исполняется, не читаясь».

## 7. Внедрение: шестишаговый процесс создания
> Место в рамке: уровень 3

С принципами и архитектурой выше skill-creator даёт шестишаговый процесс — из идей в исполняемые шаги (см. схему рамки в главе 3).

### 7.0 Правила именования

Сначала зафиксируйте имя:

- только строчные буквы, цифры и дефисы; имя от пользователя нормализуйте в hyphen-case (например, «Plan Mode» → `plan-mode`)
- длина имени ≤ 64 символа
- предпочтительны короткие фразы, начинающиеся с глагола и описывающие действие
- при необходимости — пространство имён по инструменту (например, `gh-address-comments`, `linear-address-issue`)
- имя папки навыка полностью совпадает с именем навыка

### 7.1 Step 1: понять навык — закрепить согласие на конкретных примерах

> Skip this step only when the skill's usage patterns are already clearly understood.

Чтобы создать эффективный skill, сначала нужно ясно понять **конкретные сценарии использования**. Источник — примеры от пользователя или сгенерированные и подтверждённые пользователем примеры.

Для навыка image-editor можно спросить:

- «Какие функции должен поддерживать image-editor: редактирование, поворот, ещё что-то?»
- «Можете привести примеры использования этого навыка?»
- «Представляю фразы вроде „убери красные глаза с фото“ или „поверни картинку“. Какие ещё способы использования?»
- «Какими словами пользователь будет запускать этот навык?»

**Важно**: не задавайте слишком много вопросов сразу. Сначала самое важное, потом — по необходимости.

**Критерий готовности**: ясное понимание, какие функции навык должен поддерживать.

### 7.2 Step 2: спланировать переиспользуемое содержимое навыка

Для каждого конкретного примера два анализа:
1. Если делать это с нуля — что понадобится?
2. Что из этого будет использоваться снова и снова?

Повторяющееся → упаковать в scripts/references/assets.

Skill-creator даёт три типичных разбора:

**Кейс 1: навык `pdf-editor`** (пользователь: «поверни этот PDF»)
- поворот PDF каждый раз требует одного и того же кода
- → упаковать в `scripts/rotate_pdf.py`

**Кейс 2: навык `frontend-webapp-builder`** (пользователь: «сделай todo app» или «сделай дашборд трекера шагов»)
- фронтенд-webapp каждый раз нуждается в одних и тех же HTML/React-шаблонах
- → упаковать в каталог шаблонов `assets/hello-world/`

**Кейс 3: навык `big-query`** (пользователь: «сколько пользователей залогинилось сегодня?»)
- каждый запрос к BigQuery заново «открывает» schema таблиц и связи
- → упаковать в `references/schema.md`

**Критерий готовности**: список всех переиспользуемых ресурсов для включения (scripts, references, assets).

### 7.3 Step 3: инициализировать навык

> When creating a new skill from scratch, always run the `init_skill.py` script.

Здесь стоит «always» — не «желательно», а «всегда». Почему:
- структура каталога из скрипта соответствует спецификации
- TODO в шаблоне не дают забыть обязательные поля
- ограничения формата `agents/openai.yaml` (длина полей, кавычки) при ручной правке легко нарушить

Это **прямое применение принципа низкой свободы**: инициализация — хрупкая операция, скрипт убирает риск ошибки.

После инициализации:
- настройте SKILL.md и при необходимости добавьте ресурсы
- если использовали `--examples` — замените или удалите файлы-заглушки

### 7.4 Step 4: отредактировать навык

Самый важный шаг, в две фазы:

#### Фаза 1: сначала реализуйте переиспользуемые ресурсы

Начните с ресурсов из Step 2: файлы в `scripts/`, `references/`, `assets/`.

Замечания:
- может понадобиться ввод пользователя (например, навыку `brand-guidelines` нужны бренд-материалы)
- новые скрипты **обязательно прогоните реальным запуском**, чтобы не было багов и вывод совпадал с ожиданиями
- если скриптов много похожих — достаточно протестировать представительную выборку
- если использовали `--examples` — удалите ненужные файлы-заглушки. Создавайте только реально нужные каталоги ресурсов

#### Фаза 2: обновите SKILL.md

**Как писать frontmatter**:

```yaml
---
name: skill-name
description: >-
  Опиши, что делает навык + когда именно его использовать.
  Всю информацию «when to use» клади сюда, не в body.
---
```

**Как писать body**:

Операционные инструкции для другого экземпляра Codex. Включайте то, что полезно Codex, но неочевидно: процедурные знания, предметные детали, как пользоваться переиспользуемыми ресурсами.

Единый **повелительный / инфинитивный** тон.

### 7.5 Step 5: проверить навык

```bash
scripts/quick_validate.py <path/to/skill-folder>
```

Проверка формата YAML frontmatter, обязательных полей, правил имён. Не прошло — исправьте и запустите снова.

### 7.6 Step 6: итерация

> After testing the skill, users may request improvements. Often this happens right after using the skill, with fresh context of how the skill performed.

Workflow итерации:
1. Используйте навык на реальной задаче
2. Найдите места, где тяжело или неэффективно
3. Определите, что обновить в SKILL.md или связанных ресурсах
4. Внесите изменения и протестируйте снова

Хороший skill редко получается с первого раза. Навык laotou-thought-style, созданный skill-creator, после первой генерации уже итерировал `short_description` и `default_prompt` в `openai.yaml` — от общих формулировок к более точным операционным инструкциям.

## 8. Итог

Вернёмся к исходному вопросу: как написать хороший skill?

Обзор всей рамки:

```
Корневое ограничение: краткость (глава 4)
 ├── Куда класть информацию? → три уровня, загрузка по необходимости (глава 5)
 ├── Сколько свободы ИИ? → хрупкое — скриптом, творческое — текстом (глава 6)
 └── Как внедрить? → шесть шагов: понять→спланировать→инициализировать→отредактировать→проверить→итерировать (глава 7)
```

**Skill — это инструкции для ИИ, а не для человека. Минимумом токенов, на верном уровне, дайте ИИ самые точные ограничения — и пусть он свободно действует внутри этих границ.**
