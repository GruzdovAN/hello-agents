## 1. Архитектура мультиагентов и параллельное планирование

<strong>Q1. Как в мультиагентной системе реализовать «многопоточный параллелизм»? Как сделать так, чтобы шаги, которые планировщик (planning Agent) выделил как параллельные, сами подхватывались исполнительными агентами с учётом зависимостей? Есть ли готовые фреймворки?</strong>

- Кратко:
  - Сначала «агент-планировщик» (task planning Agent) раскладывает задачу по зависимостям: часть подзадач можно выполнять параллельно, часть — только по порядку.
  - На уровне исполнения удобно держать несколько специализированных агентов: каждый берёт только свои подзадачи.
  - Параллельный планировщик обычно строится на очередях / опросе API и т.п.; почти всегда нужна донастройка под бизнес. Универсального «включил и забыл» почти нет.
- Где в курсе: главы про мультиагентные парадигмы и системную архитектуру (классические схемы + практика на фреймворках).

## 4. Знания и инструменты: RAG / KAG / граф знаний / RL и др.

<strong>Q3. Обязателен ли RAG при сборке агента?</strong>

- Кратко:
  - RAG — не обязательная часть агента, а распространённый «внешний знаниевый инструмент».
  - В <strong>главе 8</strong> с нуля собирается схема RAG, чтобы увидеть разницу «с RAG / без RAG» в дизайне системы.
- Где в курсе: глава 8.
- 🔗 [Глава 8. Память и поиск](../docs/chapter8/Chapter8-Memory-and-Retrieval.md)

<strong>Q21. Как KAG / граф знаний связаны с агентом?</strong>

- Кратко:
  - KAG / граф знаний удобно мыслить как «инструмент» или «знаниевый фундамент» агента:
    - агент решает и вызывает;
    - граф даёт структурированные знания и поиск.

<strong>Q22. По классификации главы 1 («обучаемый Agent vs Agent на LLM»), куда относятся RL, LLM и RLHF?</strong>

- Кратко:
  - RL, LLM и RLHF скорее <strong>составные части или техники реализации</strong> агента, а не отдельный «тип агента».
  - Например: LLM — «мозг» агента; RL / RLHF — обучение или донастройка политики агента.

<strong>Q18. В workflow ReAct инструмент веб-поиска serpApi — есть ли замены?</strong>

<strong>Q21. Reasoning-модель отдаёт только потоковый вывод и не входит в последующий цикл агента</strong>

- Кратко:
  - У DeepSeek, Qwen и подобных reasoning-моделей по умолчанию часто только streaming API; нужно корректно собрать поток (не простой `+` строк). Как именно — см. главу 7.

<strong>Q23. Не понимаю, как связать память и базу знаний.</strong>

- Кратко:
  - Аналогия: у агента обычно есть краткосрочная и долгосрочная память. Краткосрочная — «что делали сегодня»: её можно целиком положить в контекст как input. Долгосрочная — как конспект: всё сразу в контекст не влезет, поэтому делают инструмент: модель формирует query и через RAG достаёт нужное из базы знаний — это и есть долгосрочная память.

<strong>Q25. Вызов API модели: ошибка 401</strong>

**Q27. Открытая модель с Hugging Face: Connection aborted.**

- Кратко:
  - Сетевая причина; настройте `HF_ENDPOINT`
    - Пример: `code/chapter3/Qwen.py`
    - https://hf-mirror.com

Если ошибка вида `MaxRetryError("HTTPSConnectionPool(host='huggingface.co', port=443)` —
в код можно добавить:
```
import os
os.environ["HF_ENDPOINT"] = "https://hf-mirror.com"
```
или в командной строке
(Linux/mac)
```bash
export HF_ENDPOINT="https://hf-mirror.com"
```
(Windows PowerShell)
```bash
$env:HF_ENDPOINT = "https://hf-mirror.com"
```
